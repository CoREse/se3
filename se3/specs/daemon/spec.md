# daemon Specification

## Purpose

The resident control-plane daemon package (`se3 daemon`): discovers/supervises local `se3 run` flows, aggregates `se3/state|logs|calls|issues` state, and maintains one outbound connection to the central server.

## Requirements

### Requirement: Daemon Modules

`src/se3/daemon/` is the implementation package for the resident control-plane daemon, driven by the `se3 daemon` subcommand (registered in `cli.py`). The daemon outlives `se3 run` and is the only component that can keep aggregating state and exposing a stable endpoint after the CLI exits. New daemon submodules must be registered in this spec to prevent the LLM subprocess from being unable to discover module boundaries when CLAUDE.md is absent.

- `daemon.py` — the daemon process entry point and lifecycle: `DaemonConfig` (a config dataclass containing `pid_dir`, defaulting to `~/.se3`, overridable via `SE3_DAEMON_DIR`, and storing `daemon.pid` / `daemon_status.json` / `daemon.log` side by side, plus the optional secret `daemon_key` field — the credential the daemon presents in HELLO so the multi-tenant server can resolve it to an owner; it is sourced from `se3 daemon start --daemon-key` or the `SE3_DAEMON_KEY` environment variable, propagated to spawned `se3 run` subprocesses via the `SE3_DAEMON_KEY` child-env var, and never written to the status file or log), `Daemon` (the asyncio event loop), the `start_daemon` / `stop_daemon` / `daemon_status` functions, plus pidfile / status-file management; the `DaemonAlreadyRunning` exception. The machine-local **persistent project-root registry** also lives under `pid_dir` (the `PROJECT_ROOTS_FILENAME` constant → `DaemonConfig.project_roots_file`, e.g. `~/.se3/project_roots.json`), maintained by two helpers: `_read_project_roots(path)` (returns `[]` on missing / corrupt) and `_append_project_root(path, root)` (deduplicates by `realpath`, then atomically writes back via the existing `_atomic_write_json`); being placed under `pid_dir`, it automatically inherits the `SE3_DAEMON_DIR` / `DaemonConfig(pid_dir=...)` override and thereby naturally gains test isolation (tests isolate their writes with `DaemonConfig(pid_dir=tmp_path)` and do not pollute the real `~/.se3`). `Daemon.__init__` injects read / write callbacks based on `config.project_roots_file` (`registry_load` / `registry_persist`) into `DaemonAggregator` (using callbacks rather than a direct import to avoid a top-level aggregator↔daemon circular import), and changes the history reader's `project_roots_provider` from `aggregator.project_roots` (the bare active set) to `aggregator.all_project_roots`, so that `build_index` can still obtain the registry roots and correctly list on-disk history even with zero live processes or after a daemon restart
- `supervisor.py` — `DaemonSupervisor`, discovers and supervises the local `se3 run` processes (via `psutil` scanning and `engine.json` reading), tracking process lifecycle and cleanup. **Worktree attribution.** A `se3 run --worktree` flow body executes with its `cwd` inside `<main_root>/se3/worktrees/<name>/`, which is a transient isolation sandbox — NOT a project in its own right. When the supervisor discovers a process whose `cwd` lives under a `se3/worktrees/` directory, the module-level helper `resolve_worktree_main_root(path)` MUST map it back to the owning `<main_root>` (stripping exactly **one** `/se3/worktrees/<name>` suffix level, so a nested worktree resolves to its immediate parent, not the top), and the process MUST be attributed to `<main_root>` rather than registered as its own standalone project root; the companion predicate `is_worktree_copy_root(path)` identifies such worktree-copy roots so the aggregator can exclude them (see `aggregator.py`). This keeps the worktree sandbox out of the web console's project list and prevents the worktree copy from polluting the project-root registry
- `spawner.py` — `DaemonSpawner`, spawns new `se3 run --output-format json` subprocesses on others' behalf via `subprocess` (supporting remotely published new tasks), managing their arguments and environment; the `SpawnedProcess` record. It also exposes the `ensure_se3_project(project_root)` hook: it checks whether `<project_root>/se3/specs/base/spec.md` exists; if not, it runs `se3 init -p <project_root>` as a subprocess to complete initialization, and re-validates that the marker file exists after init returns; a failure at any stage is reported back to the caller via a structured `EnsureResult` / equivalent error (`client._handle_spawn` goes straight to the SPAWN_FAILED channel on ensure failure and does not proceed to spawn); when the directory is already an se3 project it is admitted directly, skipping init. Every time `client.py` handles `MSG_SPAWN_FLOW` it must call this hook first, then delegate to the original spawn flow. The argv prefix when spawning an `se3` subprocess is resolved uniformly by the module-level helper `_resolve_se3_command()`, and all spawn paths (`spawn` / `spawn_init` / `spawn_run`) share its result; it is **strictly forbidden** to bypass it and call `shutil.which('se3')` directly or hardcode the `"se3"` literal — the bin directory of the daemon's own Python environment is not necessarily first on PATH (a typical scenario: the daemon runs in `~/.se3-stable` while a pixi/pip environment's bin directory comes earlier on PATH), and resolving by PATH would hit an older se3 console script in another environment, causing cross-version regressions such as the subprocess writing a `se3_version` into `_meta.json` that disagrees with the daemon, the discovery three-part user-content markers being absent, and `StreamJSONTracker` no longer writing `stream_progress` to the jsonl. `_resolve_se3_command()` uses a **same-prefix first** three-level fallback: (1) it prefers `Path(sys.executable).parent / 'se3'` (also probing `se3.exe` on Windows), returning `[<console_script>]` if it exists, guaranteeing the subprocess shares the same Python environment, wheel, and version as the daemon; (2) if the same-prefix one does not exist, it falls back to `[sys.executable, '-m', 'se3']`, reusing the same interpreter to load the `se3` package and avoiding PATH interference; (3) lastly it chooses `shutil.which('se3')` (effective only in extreme packaging scenarios such as a missing `sys.executable`). The return type stays `List[str]` (which may be a single-element `[path]` or `[python, '-m', 'se3']`), so the three call sites need no distinction when concatenating `argv`. To make configured agent commands resolvable when the daemon is started from an **impoverished launch environment** (systemd / cron / container), the spawner performs a one-time VSCode-style login-shell PATH resolution at construction time and merges its result into every spawned child's `PATH`: when the daemon is launched by systemd (`/etc/systemd/system/se3-daemon.service`, no `Environment=` line) it inherits systemd's minimal default `PATH` (`/usr/local/sbin:/usr/local/bin:/usr/sbin:/usr/bin`) which excludes `~/.local/bin`, so a flow spawned via `os.environ.copy()` inherits that bare `PATH`, and `claude_runner._run_single_with_monitor`'s `shutil.which(cmd)` then fails for every configured agent command (`dclaude` / `claude` / `kclaude`, etc., all installed under `~/.local/bin`) and the runner returns returncode 127, exhausting its polls and failing discovery — whereas `se3 run` from an interactive shell does not reproduce the failure because it inherits the shell's full `PATH`. Two module-level **pure** functions implement the fix (kept pure for unit testing): `resolve_login_shell_path(timeout)` runs `$SHELL -lc 'echo $PATH'` (falling back to `/bin/bash` when `$SHELL` is unset) under a short timeout to capture the login shell's full `PATH`, returning `None` on timeout / non-zero exit; and `merge_path_env(current, login)` returns the union as a `PATH` string with login-shell entries taking precedence (login entries first, the existing entries de-duplicated and appended after). `DaemonSpawner.__init__` resolves once and caches the result in `self._login_shell_path` (the spawner is constructed during daemon startup, so this satisfies "resolve once at startup and cache"); resolution failure **MUST NOT** block daemon startup — it falls back to the prior behaviour and logs a warning. Both spawn paths — `_launch()` and `ensure_se3_project()` — after building `child_env`, set `child_env['PATH']` to the merged result whenever the cache is non-empty, so any configured agent command resolves regardless of how impoverished the daemon's own launch environment is, aligning web-UI-initiated spawns with CLI behaviour. Under a full-`PATH` environment (terminal / CLI) the merge is idempotent (the login-shell entries are already present in the inherited `PATH`), so CLI behaviour is unchanged. This is a pure code-layer fix scoped by deliberate boundaries: it does NOT modify `/etc/systemd/system/se3-daemon.service`, does NOT add a config-layer PATH fallback, and does NOT pre-check agent commands at startup (agent configuration is project-level while the daemon is user-level, so at startup there may be no project yet). When a spawn request carries a non-empty `from_issue_id`, the spawner builds an `se3 run --from-issue <id> --output-format json` argv (appending `--discover` when the request's `discover` flag is set), reusing the same `_resolve_se3_command()` / merged-`PATH` machinery as the fresh-spawn path; the request's `task_description` is ignored because the issue's content becomes the task, and the issue lifecycle (pre-start in-progress transition, recording `source_issue_id` on the flow, and the post-run resolved/open write-back keyed on exit code) is fully delegated to the CLI's existing `--from-issue` handling rather than re-implemented in the daemon. The spawner also exposes a `resume(flow_id, project_root)` path that builds an `se3 run --resume --flow-id <id> --output-format json` argv (sharing the same `_resolve_se3_command()` / merged-`PATH` machinery as the fresh-spawn path) and is the daemon-side mechanism behind a server resume request: a `MSG_SPAWN_FLOW` carrying `resume_flow_id` is routed by `client.py` to the daemon's resume handler (`Daemon._handle_resume_request` → `request_resume` → `spawner.resume`), which re-runs `se3 run --resume` against the project's existing on-disk `engine.json` so the persisted flow state supplies the task; the daemon best-effort guards against double-spawning a flow that already has a live `se3 run` process
- `aggregator.py` — `DaemonAggregator`, polls `se3/state/`, `se3/logs/`, `se3/calls/`, `se3/issues/` and aggregates them into a unified status snapshot (`MachineStatus`); `MachineStatus` also carries `project_roots: List[str]`, which the aggregator, on each snapshot round, merges from four sources via `all_project_roots()`, then deduplicates (normalizing by `realpath`) and stably sorts: (a) the roots actively registered by supervisor / spawner / client through the `_project_roots` set (containing only the active roots discovered / registered within the current process's lifetime, also the source for per-flow snapshot polling), (b) the machine-local **persistent project-root registry** (`DaemonConfig.pid_dir/project_roots.json`, see `daemon.py`) — any "project root that has run se3" is written through to disk via `add_project_root` on any registration path (spawn / ensure / resume / polling discovery, etc.), read back after a daemon restart, independent of live processes (write-through auto-registration: "run it and it's registered", with no pre-configuration needed), (c) all historical `project_root`s that `src/se3/daemon/history.py::enumerate_historical_project_roots()` adds from `se3/history/<flow_id>/_meta.json` and `se3/state/archive/engine_*.json` when it is fed the union "active roots ∪ registry roots", (d) any new root that was init-ed by `ensure_se3_project` before spawn (the client registers it back into `_project_roots` and likewise writes it through the registry via `add_project_root`). `add_project_root`, while adding to the in-memory active set, best-effort writes through to the persistent registry (deduplicated; the I/O is done via the injected `registry_load` / `registry_persist` callbacks), concentrating persistence at a single write-through point rather than scattering it across the four registration call sites, ensuring no registration is missed; `all_project_roots()` is the sole source of this merged view, both producing `MachineStatus.project_roots` via the `_merge_project_roots` delegate and serving as the `project_roots_provider` for the history index's `build_index` (see `daemon.py` / `history.py`), so that even with zero live processes, or after a daemon restart, neither the history list nor the New Task dropdown is empty anymore; per-flow snapshot polling (`get_snapshot`) still uses only the `_project_roots` active set, avoiding polling all historical roots every tick. To keep this merged view cheap on the hot path, `all_project_roots()` always merges the **active base** (`_project_roots ∪ registry_load`) immediately, but the expensive **disk historical enumeration** (`enumerate_historical_project_roots`, which walks the whole `se3/history` tree) is throttled behind a monotonic-clock TTL cache (`HISTORICAL_ROOTS_TTL`, currently `60s`) keyed/invalidated by a fingerprint of the active base, collapsing the per-tick full traversal to at most one walk per TTL window; the cache must be invalidated correctly without busting on the routine re-add of already-known active roots, and `add_project_root` proactively invalidates it so a newly registered root's history becomes visible promptly. This removes the per-status-tick full scan of `se3/history` that — when combined with the synchronous snapshot call on the event loop (see `client.py`) — stalled the daemon during task creation; only the discovery of purely historical roots is deferred by up to one TTL window, while new active / registered roots stay immediately visible. This field is reported via `STATUS_UPDATE` to drive the Project dropdown of the web New Task form, covering the "active set is empty but historical projects are still usable" scenario after a daemon restart; when enumerating pending-response calls under `se3/calls/`, items that already have a same-named response file (`.response` / `.response.json`) are skipped, to avoid a historically already-answered call being misreported as pending; besides this sibling-response determination, `_enumerate_calls` / `_snapshot_for_root` must also decide whether a pending call is still valid based on the flow's current progress: when a call's owning `context.step_id` is no longer the flow's current step (or that step has already been processed as `COMPLETED` / `REVISION`), the call must be removed from that flow's `pending_calls` even if no `.response` sibling file was written — because interactive calls answered at the CLI terminal (`call` / `cli_confirm` / `discovery_confirm`) are usually consumed directly by the run loop without writing a sibling file, otherwise a stale "awaiting reply" chip would never clear for the whole run; a call still sitting at the current unanswered step stays pending. In addition, for the same `(flow_id, step_id)` only the latest unanswered call is kept (`_dedup_calls_by_step`): discovery's multiple clarification rounds reuse the same `step_id`, writing a new call file each round, and once an old call is superseded by a new round it becomes a stale leftover and must be removed from that flow's `pending_calls` to prevent "awaiting reply" chips from accumulating; a call whose key cannot be located (missing `flow_id` or `step_id`) does not participate in deduplication and is kept as is. Each call file's `kind` field (`call` / `interjection` / `retry_decision` / `cli_confirm`, treated as `call` when absent) is parsed and, together with the `prompt` / `context` / `options` display metadata, enriched into a `PendingCall` and reported via `STATUS_UPDATE`, so the web console can render the various pending interactions differently by `kind`. In addition to calls, the aggregator reads each project's `se3/issues/` YAML files (via `_collect_issues`) into a list of `IssueSnapshot` entries carried on `MachineStatus.issues`, so the webui issue-management panel can list / filter / view issues without a second round-trip; each `IssueSnapshot` carries the webui-relevant fields (`id`, `project_root`, `description`, `status`, `tags`, `source`, `created_at`, `updated_at`, plus the optional `title` / `priority` / `type` which are omitted when unset), defaulting a missing `source` to `system` for legacy files, and unreadable issue files are skipped so a corrupt issue never breaks the snapshot. **Worktree issue de-duplication.** A `se3 run --worktree` flow clones the project's `se3/issues/` into its sandbox, so while the run is live both the main project root and the worktree-copy root would otherwise be aggregated and every issue would be counted twice. The aggregator MUST therefore skip issue collection for any project root that is a worktree copy (`is_worktree_copy_root`, see `supervisor.py`): during a worktree run only the main project's issues are authoritative, and the worktree copy's `se3/issues/` are ignored, so the webui issue list and counts are not doubled. (This is the same `se3/worktrees/` attribution that keeps the worktree directory out of the project list.) **Promoted worktree terminal state.** Because the merge-back promotes a completed worktree flow's terminal `engine.json` into the main project's `se3/state/archive/engine_<flow_id>.json` (see the `se3-workflows` spec), the aggregator/history layer reports that promoted snapshot as a `completed` flow exactly like an ordinary archived run, with no worktree special-case
- `client.py` — `DaemonClient`, maintains one outbound WebSocket connection to the central server (the daemon dials in actively, NAT-friendly), reporting aggregated status, receiving dispatched commands, and routing them to supervisor / spawner; the `websockets.connect` call is given `max_size=protocol.MAX_WS_MESSAGE_BYTES` so the daemon's inbound frame limit is lifted off the library's 1 MiB default to the shared protocol cap (set symmetrically for future large server→daemon frames, even though the daemon's send direction is unbounded by `max_size`); reconnects with exponential backoff after a disconnect; after connecting, reports the historical session index (`MSG_HISTORY_INDEX`), pushes active sessions' historical data in incremental append mode (`MSG_HISTORY_DATA`), handles inbound on-demand history pull requests (`MSG_HISTORY_REQUEST`) by replying with `MSG_HISTORY_DATA`, and handles inbound index re-push requests (`MSG_HISTORY_INDEX_REQUEST`) — upon receipt it calls `_push_history(ws, force_index=True)` to force a rebuild and immediately re-push the latest history index (`force_index=True` bypasses the `engine.json`-change-based debounce so that a waiter suspended on `GET /api/history` at the server end receives the re-push promptly and thereby obtains the latest history rather than a stale last-pushed snapshot); because `build_index` is now TTL-cached in `history.py`, the `MSG_HISTORY_INDEX_REQUEST` handler first calls the reader's `invalidate_index_cache()` before the forced re-push, and likewise the push loop invalidates whenever `_history_changed()` fires (so a real `engine.json`/jsonl change rebuilds from disk instead of returning a within-TTL stale snapshot) and the `MSG_SPAWN_FLOW` handler invalidates right after a successful spawn (so the freshly spawned flow's `engine.json` is included in both the index and the active-flow reads on the very next push instead of being delayed by the TTL window); all three call this method defensively via `getattr`, staying compatible with older reader stubs that lack it; to eliminate the runtime freeze of "the CLI has advanced but the web only sees it at the next status tick", the incremental history push is no longer driven solely by the fixed `status_interval` tick but by `engine.json` changes (detecting an `engine.json` mtime/content change triggers one mtime-debounced push), while the periodic tick is retained as a fallback; `_history_cursors` must advance correctly across ticks / across steps so that step progress of a running flow (including PAUSED/resume) is incrementally reflected to the web within one push cycle; when rebuilding the cursor table from this round's reads each round, for a **terminal flow that has no new records this round but is still an active flow in the current `engine.json`** (typically a flow waiting for `se3 run --resume` after FAILED), its existing cursor must be preserved — otherwise the flow would drop out of the cursor table after the last flush, and when `--resume` later flips the state back to RUNNING the missing cursor would force a full re-read and break the incremental push chain, freezing the web console on the failure snapshot; this preservation is bounded by the active `engine.json` flow set (one per root), so a terminal flow that has been fully read and already archived still drops out normally, keeping the cursor table bounded over the long run; handles inbound `MSG_INTERJECT_FLOW` by writing the mid-flight interjection typed in the web console as the target flow's `interjection`-kind call file, for that `se3 run` process to consume at the next step boundary. **The event loop must not be blocked by synchronous disk I/O**: synchronous calls that do heavy `Path.read_text` / directory traversal / JSON parsing — such as `HistoryReader.read_flow` in `_handle_history_request`, `build_index` in `_push_history` (including the forced rebuild / directory traversal when `force_index=True`), `read_active_flows` (fanning out to multiple per-step jsonl reads and `json.loads`), and the **`STATUS_UPDATE` snapshot construction** (the `self._snapshot_provider()` call in `_push_status`, and the same-source snapshot call in `_resolve_interject_root` and `_poll_once`) — must be executed in a worker thread via `asyncio.to_thread(...)`; the synchronous implementation stays in `daemon/history.py` / `daemon/aggregator.py`, and async only wraps a `to_thread` layer at the async entry points in daemon/client.py. The snapshot is offloaded because, through the aggregator's `all_project_roots` → `enumerate_historical_project_roots`, every status tick would otherwise walk the whole `se3/history` directory and read each `_meta.json` synchronously on the event loop; once history grows large this single synchronous traversal is enough to stall the loop, so the daemon misses heartbeats (the server's `HEARTBEAT_TIMEOUT` greys the machine out), drops inbound `SPAWN_FLOW` (no `SPAWN_FLOW handled`), and cannot even drive reconnection during the stall — manifesting as "creating a task in the web UI greys the machine out and it does not auto-recover until the daemon is manually restarted". This is so that when a session containing a large jsonl is selected, or a task is being created, the daemon can still keep responding to PING/PONG, PUSH, and new commands within the window of the server-side `HISTORY_PULL_TIMEOUT` and the client heartbeat timeout (`HEARTBEAT_TIMEOUT`), avoiding the cascading regression of "504 while pulling history, the daemon judged offline at the same time, the machine greying out in the UI, and reconnect backoff triggered"; lightweight probe paths that only `stat` (such as signature scans like `active_flow_signature`) may stay synchronous and need no `to_thread`. When handling `MSG_SPAWN_FLOW`, the client first calls the daemon-internal ensure path (`_handle_ensure_request` → `spawner.ensure_se3_project`): if the target `project_root` is not an existing se3 project, it first runs `se3 init` as a subprocess on the daemon host, and on success registers the root into the aggregator's `_project_roots` before continuing the standard spawn flow; on ensure failure it notifies the server via the existing spawn-failure reporting channel (`SPAWN_FAILED` / equivalent error receipt) and does not enter the spawn phase. For the multi-tenant control plane, `DaemonClient` carries an optional `daemon_key` (empty for local / legacy single-tenant operation) and passes it into `make_hello` so the server can resolve `key → owner_id` and bind this machine to a trust domain; the key lives only in memory and on the HELLO wire and is never logged. On receiving the server's `WELCOME`, the client honours an `accepted=false` rejection (e.g. unknown/invalid daemon key): it records the server-supplied `reason` (which never contains the key), stops replaying the rejected key in a tight reconnect loop, and surfaces a message telling the operator to re-issue / fix the daemon key and restart, rather than hammering the server with a credential it has already rejected (the key is sourced once at daemon startup — see `DaemonConfig.daemon_key` below — and threaded through HELLO only). When handling `MSG_SPAWN_FLOW`, the client inspects the payload's optional `resume_flow_id`: when present it routes to the daemon's `resume_handler` (resuming the named flow via `spawner.resume` rather than a fresh spawn, skipping the `ensure_se3_project` init hook since a resumable flow's project already exists); when absent it follows the original ensure-then-spawn path. The client also handles `MSG_ISSUE_COMMAND` (`_handle_issue_command`): it validates the `project_root` (which must be an absolute, registered SE3-project path) by reusing the `project_roots` set cached from the most recent `STATUS_UPDATE` snapshot (`self._last_known_project_roots`, recorded by `_push_status` whenever it successfully builds a snapshot), falling back to building a single snapshot via `_snapshot_provider` **only** when that cache is still absent (e.g. an issue command arrives before the first `STATUS_UPDATE`); it MUST NOT re-invoke the heavyweight `_snapshot_provider` (which walks the whole `se3/history` tree) on every issue command, because that repeated heavy call on the issue hot path — racing the periodic status/history pushes that share the same ws connection — is what delayed the ack past the server's `ISSUE_COMMAND_TIMEOUT` and produced the "issue already landed on disk but the web reported a timeout failure" false negative. After validation it executes the `create` / `edit` / `close` / `reopen` `operation` against `IssueManager` off the event loop (CLI/webui issue writes use `source="human"`). On a successful write it sends the `MSG_ISSUE_RESULT` ack (echoing `request_id`, reporting `ok` / `error` / affected `issue_id`, so the server can correlate the acknowledgment) **before** triggering the fast status push, not after: the ack is the frame the server blocks on within `ISSUE_COMMAND_TIMEOUT`, and `_trigger_fast_push` (which only schedules a follow-up `STATUS_UPDATE`) must not be allowed to occupy the ws send order ahead of it — sending the ack first minimizes end-to-end ack latency while leaving the on-disk persistence semantics unchanged; the fast push still runs afterwards so the web reflects the issue change on the next tick
- `history.py` — historical session index construction and cursor-based incremental reading: enumerates `se3/history/` and `se3/state/archive/` to build the historical session index (task description, status, time, etc.), distinguishing active / inactive sessions; the `task_description` shown for a history-only flow (the list title) is recomputed live from the flow's first `*.jsonl` on every index build by `_extract_history_summary` — it is NOT persisted in `_meta.json`, so the title self-heals on existing flows with no data migration. That extractor follows a three-tier priority aligned with the web chat-history user bubble: (1) the user's literal input cut out by the shared `prompt_markers.extract_user_content` (the `USER_CONTENT` marker split, mirroring `splitUserPromptByMarker`); (2) failing that, the embedded `Task description:\s*-+\s*(.*?)\s*-+` block (the first-step-not-discovery `se3 run "task"` flow); (3) failing that, the raw first-line content untruncated (the index caller applies its own `_clip`). The CLI counterpart `PersistenceManager.extract_history_summary` (see the se3-commands spec) applies the identical three-tier priority, differing only in that it clips its own result to 100 characters. Reads incrementally by per-flow per-step jsonl file cursors, so an active session's conversation records can be reported incrementally without re-sending the whole jsonl each round. While reading, it also parses the authoritative step_type from each per-step jsonl filename (convention `NN_<step_type>_<hash>(_Gk)`) and injects it at the envelope layer, so each reported record looks like `{step_id, step_type, message}`: the raw `message` pushed by the daemon itself does not contain step_type, and after injection the frontend no longer has to guess from the filename, while the `message` content is left untouched to maintain backward compatibility and raw visibility. The parsing is done by the pure function `parse_step_type_from_step_id(stem)` — after stripping the leading `NN_` sequence number, the trailing `_G\d+` group suffix, and the trailing hexadecimal hash segment, it takes the remaining middle segment (which may itself contain underscores, e.g. `version_analyze`) as the step_type, softly validated against the built-in `_KNOWN_STEP_TYPES`; when the naming convention is followed but the type is unregistered it still returns the parsed middle segment (self-describing, drift-tolerant), while an old name with no sequence number and no hash (e.g. `commit_summary`) falls back to the original stem, never raising. The "active" determination of `read_active_flows` must cover **in-progress** flows (including `PAUSED` waiting for user input and the `--resume` continuation state), and must not prematurely drop a flow merely because it is not at the RUNNING terminal value, otherwise the web would freeze during a run and only catch up all at once after archiving; the incremental cursor must advance correctly on each round's read — newly appearing per-step jsonl files and appended lines of the same file must all be taken in, achieving **no loss, no duplication, no truncation of subsequent reads** (a record once read is never re-read, and an unread tail continues next round). To keep the daemon's per-fast-tick push loop (`client.py::_push_loop` → `_push_history`, which calls `build_index` every ~1s tick) from re-walking the whole `se3/history` tree every second — a second event-loop-starvation source distinct from, but of the same class as, the aggregator's `enumerate_historical_project_roots` walk already throttled by `HISTORICAL_ROOTS_TTL` — `build_index` caches its result behind a monotonic-clock TTL (`BUILD_INDEX_TTL`, currently `3s`): within the window it returns the cached `SessionMeta` list and only the uncached `_build_index_fresh()` performs the full directory walk + JSON parse, collapsing the repeated identical per-tick rebuilds into at most one walk per window. `invalidate_index_cache()` drops the cache so the next `build_index` rebuilds from disk; it is called on every real disk change (the push loop invalidates when `_history_changed()` fires), right after a flow is spawned, and before a forced index re-push (all three call sites live in `client.py`), so a newly spawned or just-changed flow becomes visible promptly rather than waiting out the TTL. Because the cached index may carry **stale `active` flags** for up to the TTL window, `read_active_flows` no longer trusts `meta.active` directly: it re-checks each candidate's live status via `_is_still_active`, a lightweight single-`engine.json` `stat` + small JSON parse (dramatically cheaper than the full rebuild it replaces) that confirms the on-disk `engine.json` still describes *this* `flow_id` (guarding against a different flow having since become the active `engine.json` flow, which would otherwise keep the stale meta in the active set and miss the new flow) and that its status is still an active one — so liveness is preserved (any real `engine.json` / jsonl change invalidates and rebuilds fresh, and the per-flow re-check catches within-window status flips) while the TTL collapses the redundant full walks that were starving the event loop. It also exports the helper `enumerate_historical_project_roots() -> list[str]`: it traverses `se3/history/<flow_id>/_meta.json` and `se3/state/archive/engine_*.json`, extracts each record's `project_root` field, and deduplicates and sorts them, for `aggregator.py` to merge into `MachineStatus.project_roots` when rebuilding the snapshot; when fed the union "active roots ∪ persistent registry roots" (rather than the active set only), it supplements each root in the union with its on-disk history roots, robustly skipping non-directory / artifact-less roots without raising. The two WARNING points that report an unreadable / corrupt archive or `_meta.json` file (`history: skipping unreadable meta file ...` and the sibling archive-file warning) are **per-file deduplicated** (`_warn_once_unreadable`): the first encounter of a given path logs at WARNING, and every subsequent encounter of the same path is demoted to DEBUG, so a small set of permanently corrupt meta files can no longer flood `daemon.log` (the observed failure produced a ~210MB / ~1.26M-line log from four corrupt `_meta.json` re-warned every tick). This dedup is a defence-in-depth backstop independent of, and complementary to, the TTL throttling of the enumeration in `aggregator.py` (which already drives the warning frequency down at the source); the corrupt files themselves are left in place and continue to be ignored. The `project_roots_provider` of the history index construction (`build_index`) is injected by the daemon as `aggregator.all_project_roots` (the ordered union of active roots ∪ registry roots ∪ the aforementioned on-disk history roots), replacing the previous approach of directly reading the bare active set `aggregator.project_roots` — the latter is empty when "this machine currently has no se3 run process", which was exactly the root cause of the history list previously always coming up empty (`No history sessions reported.`); after switching to `all_project_roots`, the history index is still non-empty with no live processes, or even after a daemon restart. To eliminate a second-order regression that 57b1609 (8.11.2)'s `BUILD_INDEX_TTL` cache addressed only partially — where the per-tick push loop still rebuilt the index roughly once per second (an active flow writing to disk every second fires `invalidate_index_cache()` via `client.py`, defeating the 3s TTL), and each `_build_index_fresh()` rebuild called `_extract_history_summary` on every history-only directory lacking a `_meta.json`, which read the entire first jsonl via `read_text()` just to take its first line (observed: 161 such directories, ~115MB of first jsonl including a single 30MB stale discovery log, sustaining ~100MB/s logical reads with a single core pinned at ~92% CPU by CPython's UTF-8 decode at ~104 MB/s; ZFS arcstats confirmed the reads were ~99.4% ARC-cache hits so the cost was single-core CPU burn and degraded daemon responsiveness rather than physical-array wear) — the whole-file reads in `history.py` are replaced by bounded reads via three changes:
  1. `_extract_history_summary` streams only the first line (`open()` + `readline()`) instead of `read_text()`, so recovering a title never reads the whole file; its three-tier output (the `prompt_markers.extract_user_content` user literal, then the `Task description:` block, then the raw first line) is unchanged, so the daemon→web title and its CLI counterpart (`PersistenceManager.extract_history_summary`, see the se3-commands spec) stay aligned.
  2. `DaemonHistoryReader` gains a process-internal per-directory meta cache (`self._history_meta_cache: Dict[str, Tuple[signature, SessionMeta]]`) keyed by a cheap directory content signature (the set of jsonl filenames + the latest mtime + total size, computed by reusing the existing `iterdir`/`stat` traversal); `_meta_from_history` returns the cached `SessionMeta` on a signature hit and only parses + back-fills on a miss, so a `_build_index_fresh` rebuild re-parses only the directories whose signature actually changed (an active flow's per-second write changes only its own directory's signature, while the other ~161 static directories all hit the cache). This is a process-internal optimization only: it does NOT write to disk and does NOT back-fill `_meta.json` into project directories (the daemon never writes into project directories on their behalf). It layers beneath the existing `BUILD_INDEX_TTL` cache: the TTL cache suppresses an entire rebuild on a no-change tick, while the per-directory signature cache suppresses re-parsing the unchanged directories during a rebuild that a real change did trigger.
  3. `read_flow` reads active flows incrementally by **byte offset** instead of `read_text().splitlines()` re-reading the whole jsonl every push and slicing by a line-number cursor. A process-internal `self._read_offsets: Dict[str, Tuple[consumed_lines, byte_offset, mtime, size]]` keyed by absolute jsonl path lets a push seek to the recorded offset and read only the appended bytes when the caller's line cursor matches the recorded consumed-line count and the file size is ≥ the recorded offset; otherwise (first read / cursor rewind / file truncated-and-replaced) it falls back to a from-scratch full read and rebuilds the offset, with the UTF-8 byte-boundary seek handled correctly. The handling of an **un-terminated trailing line** (a final line not closed by `\n`) MUST branch on JSON parseability rather than always being deferred: a trailing line that already parses as a complete JSON record — the normal shape of a terminal-written file and of every `*.jsonl.from-<branch>` merge-back sidecar, whose final (and, for a single-record file, only) record is frequently flushed without a closing newline — is **consumed** and advances the offset, while a tail that does not yet parse (a genuine mid-write truncated line) is **left intact** (consumed-line count and byte offset are NOT advanced) so it is re-read once the writer completes it. This is the root cause of the worktree/discovery symptom-B "first assistant body empty, then nothing further": the prior "only consume `\n`-terminated lines" rule deferred the complete-but-unterminated first/only record indefinitely, so the worktree session's first assistant record read as empty and the cursor never advanced past it. The parseability branch keeps the prior write-race safety (a half-written line is still never skipped-and-dropped) while no longer starving a complete record of its trailing newline. The external `FlowRead` line-number cursor semantics and the pushed `records` content are preserved item-for-item, so server / webui keep using the `{jsonl-filename: line-count}` cursor unchanged; the offset table is reader-internal optimization state that never enters the wire protocol, so after a daemon restart it cold-starts and the first round degrades to a single full read, with correctness independent of it.
  The remaining file-read point `_read_json` was reviewed and left unchanged because it only reads small JSON files; these are the three file-read points in `history.py` (the first-jsonl title extractor, the active-flow incremental reader, and `_read_json`).

  **Worktree merge-back sidecar files.** When a `se3 run --worktree` flow merges back, each worktree per-step history file is written into the main session directory not as a plain `*.jsonl` but as a collision **sidecar** named `<base>.jsonl.from-<branch>` (e.g. `01_discovery_ab12.jsonl.from-worktree__b`), because the logical-step file may already exist in the main session. A reader that enumerates only `glob("*.jsonl")` never matches these sidecars, so every record after the first is dropped and the frontend renders empty content as "(no readable content)". The history reader MUST therefore enumerate **both** the primary `*.jsonl` files **and** their `*.jsonl.from-<branch>` sidecars, and merge them under one **logical step id**: the pure helper `parse_step_type_from_step_id` / the step-id reduction strips the `.jsonl` extension together with any trailing `.from-<branch>` sidecar suffix (and a possible trailing hash) before parsing `step_type`, so a step's primary file and each of its sidecars resolve to the same logical step and stream together. Because the incremental read cursor is keyed by **absolute file path**, each primary and each sidecar advances independently, so a worktree merge-back that only appends sidecar records is still picked up with no loss, no duplication, and no truncation — both the running-flow live stream and the post-merge completed history of a `--worktree` session display in full, exactly like an ordinary in-place session. **`project_root` preservation across the worktree read path.** A worktree / discovery session's history lives under a `project_root` that the bare active set does not necessarily surface, so the reader MUST locate it by the correct root rather than guessing: `read_active_flows`'s **final-flush** pass (the last incremental read that drains a flow's tail) MUST call `read_flow(flow_id, cursor=cursor, project_root=<that flow's own root>)` — it builds a `root_by_flow` map so each flow is flushed against its own `project_root` instead of an unscoped or wrong-root call — and `_resolve_flow_dir` MUST be able to resolve a worktree session's on-disk history directory from that `project_root` (covering the worktree main-root attribution). Without the scoped `project_root`, `_resolve_flow_dir` searched the wrong root set, the worktree flow's directory was not found on the flush, and its first and subsequent records never reached the live view — the read-side half of symptom B that the trailing-line parseability fix (above) complements. The `respond` / `interject` write path likewise preserves the worktree session's `project_root` (see `client.py` / `_resolve_interject_root`) so the call `.response` and the history read agree on the same root
- `protocol.py` — the single source of truth for the daemon↔server WebSocket protocol: `PROTOCOL_VERSION` (currently `"2"`), `DEFAULT_SERVER_PORT` (the central server's default port `8080`, referenced by both the `--port` default of `se3-server` and the daemon client's URL port completion), `MAX_WS_MESSAGE_BYTES` (the shared daemon↔server WebSocket single-frame size cap, currently `256 * 1024 * 1024` = 256 MiB; both ends import this one constant so the inbound size limit cannot drift between them — the daemon passes it as `max_size` to `websockets.connect` and the server passes it as `ws_max_size` to `uvicorn.run`, lifting the libraries' much smaller defaults (`websockets`' 1 MiB and `uvicorn`'s 16 MiB) that would otherwise silently drop an oversized `MSG_HISTORY_DATA` frame and surface as a `GET /api/history/{flow_id}` 504; a bounded large value is used rather than `None` so a pathologically large frame still has a memory ceiling), the message-type constants (`MSG_HELLO` / `MSG_WELCOME` / `MSG_STATUS_UPDATE` / `MSG_SPAWN_FLOW` / `MSG_RESPOND_CALL` / `MSG_CALL_NOTIFICATION` / `MSG_PING` / `MSG_PONG`, plus the history-related `MSG_HISTORY_INDEX` (daemon→server historical session index) / `MSG_HISTORY_INDEX_REQUEST` (server→daemon, requesting the daemon to rebuild and immediately re-push its historical session index, registered into `SERVER_TO_DAEMON` / `ALL_MESSAGE_TYPES`) / `MSG_HISTORY_REQUEST` (server→daemon, on-demand pull of a historical session's records) / `MSG_HISTORY_DATA` (daemon→server historical-data response, supporting full / append modes and a cursor), plus `MSG_INTERJECT_FLOW` (server→daemon, dispatching one mid-flight interjection typed in the web console to a running flow)) and the `make_*` message constructors (including `make_history_index` / `make_history_index_request` / `make_history_request` / `make_history_data` / `make_interject_flow`; `make_spawn_flow` adds a `discover` field to pass through the "start from discovery" flag, **and an optional `resume_flow_id` field** — when non-empty it is included in the payload and instructs the daemon to *resume* the named flow (`se3 run --resume --flow-id <id>`) rather than start a fresh one, with `task_description` ignored in that case; when empty it is omitted from the wire so a fresh-spawn payload is unchanged and stays backward compatible. `make_spawn_flow` further accepts an **optional `from_issue_id` field**: when non-empty it is included in the payload and instructs the daemon to start the flow from the named issue (`se3 run --from-issue <id>`), in which case the request's `task_description` is ignored in favor of the issue's content and the issue lifecycle is driven by the CLI; it MAY be carried together with the `discover` field (start-from-discovery on an issue), and when empty it is omitted from the wire so existing fresh-spawn payloads are byte-for-byte unchanged and no `PROTOCOL_VERSION` bump is required). The module also defines the **issue write-command message pair** for the webui issue-management surface: `MSG_ISSUE_COMMAND` (server→daemon, registered in `SERVER_TO_DAEMON`) carries an `operation` of `create` / `edit` / `close` / `reopen`, a required `project_root`, operation-specific fields (`issue_id`, `description`, `title`, `priority`, `type`, `tags`, `reason`) and an optional `request_id`; `MSG_ISSUE_RESULT` (daemon→server, registered in `DAEMON_TO_SERVER`) echoes the `request_id` with `ok=true` or `ok=false`+`error` (and the affected `issue_id`) so the server can correlate the acknowledgment. Their constructors are `make_issue_command(operation, project_root, *, issue_id, description, title, priority, type, tags, reason, request_id)` (which omits unset optional fields, and where for `edit` a `None` field means "leave unchanged" while an empty string means "clear") and `make_issue_result(request_id, *, ok, error, issue_id)`. This module also centrally defines the `kind` constants `CALL_KIND_*` (`CALL_KIND_CALL` / `CALL_KIND_INTERJECTION` / `CALL_KIND_RETRY_DECISION` / `CALL_KIND_CLI_CONFIRM`) and the `CALL_KINDS` set for the running-flow human-interaction call files, so that the `kind` value of call files under `se3/calls/` does not drift among the engine, the daemon, and the server. It is imported by both the daemon and the `se3.server` package, ensuring the protocol schema does not drift. A peer encountering an unknown `type` should ignore it, to guarantee that mixed old/new version connections do not crash. For the multi-tenant control plane, `make_hello(machine_id, hostname, se3_version, key="")` carries an **optional** `key` field — the daemon credential the server resolves to an owner (`key → owner_id`) to bind the reporting machine to a trust domain; the field is omitted from the wire when `key` is empty, so a keyless daemon and an older single-tenant server stay wire-compatible (no `PROTOCOL_VERSION` bump), and the key is a secret that MUST NEVER be logged. `make_welcome(server_version, accepted=True, reason="")` carries the `accepted` flag and a (key-free) `reason` string so the server can reject an unauthenticated/invalid-key HELLO with `WELCOME(accepted=false)`
