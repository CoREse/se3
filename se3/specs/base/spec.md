# SE3 Framework — Base Specification

## Purpose
Project baseline conventions. This spec is generated by `se3 init` and is automatically loaded in every `se3 run` flow.

## Requirements

### Requirement: Project Identity
- Project name: SE3 Framework
- Summary: the SE 3.0 code-first software-engineering flow engine — a pure CLI flow engine; code is primary, and the spec is a documented snapshot of the code's current state (a spec-assistant), refreshed from the code by `se3 sync`
- Primary language/framework: Python 3.8+, Typer (CLI), PyYAML, Rich, prompt-toolkit

### Requirement: Directory Structure
- `src/se3/` — framework source code (a pip-installable package)
  - `cli.py` — CLI entry point; registers all commands
  - `commands/` — implementations of the individual CLI subcommands
  - `engine/` — flow engine core (state machine, steps, context builder, LLM caller)
    - `engine/sync_engine.py` — the `se3 sync` single-round stateless engine (spec ↔ code drift analysis and write-back); `run_once` accepts each round's analyze_specs subset and the do_discovery flag, aggregates the files touched by each spec's analyze this round into cumulative deps, and exposes the count of newly discovered subsystems this round along with the obsolete-spec candidates
    - `engine/sync_loop.py` — the `se3 sync` cross-round orchestration (convergence detection, oscillation guard, consecutive infrastructure-failure counting, checkpoint writing, and `--resume` continuation); before the round loop it applies a level-1 global shutter and level-2 per-spec gate skip based on sync_state, within the round loop it performs a level-3 per-spec early exit (tracking each spec's consecutive zero-drift round count), and after convergence it deletes obsolete specs and writes sync_state
    - `engine/sync_analyzer.py` — spec/code comparison and LLM response parsing for the sync phase; strips the markdown fence before `json.loads`; on JSON parse failure it records `failed_analysis_reason` instead of synthesizing a fake CONFLICT diff; consumes the touched-files exposed by llm_caller for this call to support per-spec dependency tracking
    - `engine/sync_discovery.py` — within sync, discovers missing specs via the LLM and generates new specs (can be invoked every round and runs to its own convergence); a newly created spec must pass `spec_validator.validate_spec_structure(...)` before being written to disk; also provides the obsolete-spec deletion entry point `delete_obsolete_specs` (after convergence, deletes the `se3/specs/<name>/` directory; deletes directly by default, with optional per-item human confirmation)
    - `engine/sync_interaction.py` — interactive prompts for the sync flow (high-risk deletion approval, quota-exhaustion pause, etc.)
    - `engine/sync_checkpoint.py` — a lightweight persistence module for sync continuation (a schema v1 dataclass, atomic write to `se3/state/sync_checkpoint.json`, recomputing in-sync specs by SHA-256)
    - `engine/sync_state.py` — the persistent incremental-optimization cache module for sync: the `SyncState` dataclass (`state_version` / `converged_at` / `code_fingerprint` / `discovery_converged` / `spec_deps` / `obsolete_specs`), atomic write to `se3/state/sync_state.json`; JSON corruption / version mismatch / missing file all return no cache; provides `compute_code_fingerprint` (an overall hash of sorted git ls-files blob shas + the content hash of untracked, non-ignored files, excluding `se3/`), file content hashing, and file add/delete/rename detection; records the "last successful convergence" snapshot, completely different in semantics and lifecycle from `sync_checkpoint.py` (the interrupt-recovery transient state)
    - `engine/spec_validator.py` — a pure-functional spec structure validator that enforces the spec-format v1 contract (the v1 marker, the `# <name> Specification` title, `## Purpose`, at least one `### Requirement:`, a non-narrative first line); reused in three places: sync_discovery, sync_engine, and `se3 sync --validate-only`
    - `engine/state_machine.py` — the finite-state-machine core of the `se3 run` flow engine, driving transitions between steps and the flow of context
    - `engine/steps/` — the implementation package for the individual `se3 run` steps (analyze / plan / implement / verify, etc.)
    - `engine/context_builder.py` — builds context for the LLM subprocess (injecting the spec, history summary, current task, etc.)
    - `engine/llm_caller.py` — the unified entry point for LLM calls, responsible for iterating/rotating through the agent command list, detecting quota exhaustion and timeouts, and wrapping call results
    - `engine/chat_history.py` — multi-turn conversation history management and persistence
    - `engine/dag_scheduler.py` — a DAG-based task scheduler that resolves dependencies between steps/tasks and executes them in topological order
    - `engine/loop_controller.py` — flow loop control (iteration cap, exit conditions, same-state debouncing, etc.)
    - `engine/issue_discovery.py` — the issue discovery flow implementation; scans code/spec and produces pending issues
    - `engine/issue_manager.py` — reading/writing, status management, and deduplication of the issue records under `se3/issues/`
    - `engine/docs_updater.py` — documentation auto-update logic (e.g., syncing README, spec summaries, etc.)
    - `engine/version_bumper.py` — computes and bumps the version number based on the commit type (bugfix/feature) and the previous version baseline
    - `engine/version_script_interface.py` — the version-script interface adapter layer; provides discovery of the project's version-management script (probing candidate paths such as `scripts/version.py`), on-demand generation (written to disk from `templates/version_script.py.tmpl`), and a unified invocation entry point (subprocess wrappers for the `get` / `bump` / `set` subcommands), so that `engine/version_bumper.py` can read and bump the version without coupling directly to a specific script path
    - `engine/worktree.py` — the engine-side wrapper for git worktree operations, used together with the `se3/worktrees/` directory
    - `engine/merge/` — implementation related to the multi-worktree / multi-branch merge flow (see the "Engine Merge Submodules" Requirement for the specific submodules)
  - `templates/` — project-initialization templates (base spec, README, version-management script, version history, etc.)
    - `base_spec.md` — the initial template for a new project's base spec; written by `se3 init` to `se3/specs/base/spec.md`
    - `readme_md.md` — the new-project README template, containing formattable placeholders such as `{project_name}` / `{project_description}` / `{project_overview}`
    - `versions_md.md` — the new-project version-history document template (`VERSIONS.md`), containing the `{project_name}` / `{date}` placeholders
    - `version_script.py.tmpl` — the project version-management script template, providing a unified interface for the three subcommands `get` / `bump` / `set`; the output contract is: on success, print the version string to stdout and exit 0; on failure, print the error to stderr and exit 1
  - `agent_runner.py` — the Agent runner abstract base class (the `AgentRunner` ABC, `RunResult`, the `InfraErrorType` enum); defines a unified agent execution interface to ease future extension to multiple runner types (API-based, other CLIs, etc.)
  - `claude_runner.py` — the Claude Code CLI single-command adapter (`ClaudeCodeRunner`); implements the `AgentRunner` interface and is responsible for invoking the Claude Code CLI via a subprocess; agent selection/rotation is handled by `LLMCaller`; the `ClaudeRunner` alias is retained for backward compatibility
  - `config.py` — SE3 configuration management (`se3.yaml`, `se3.local.yaml` loading, git worktree main-repository root resolution, Claude subprocess config loading)
  - `utils.py` — shared utility functions (such as `discover_specs`, specs-directory resolution, etc.; supports `se3/specs/` first, `specs/` fallback, and the legacy `openspec/specs/` path)
  - `core/` — the core-utilities subpackage
    - `utils.py` — core utility functions shared across the framework (such as the `truncate_preview` formatting helper)
  - `daemon/` — the resident control-plane daemon package (the implementation of the `se3 daemon` subcommand); ships in the same package and wheel as the core and evolves in version lockstep; responsible for discovering/supervising local `se3 run` flows, spawning new flows on their behalf, aggregating `se3/state|logs|calls|issues` state, and maintaining one outbound connection to the central server (see the "Daemon Modules" Requirement for the specific submodules)
  - `server/` — the central-server backend plus bundled web frontend package; not a subcommand of the core `se3`, launched through the separate console_scripts entry point `se3-server`; the heavy web dependencies (FastAPI/uvicorn/websockets) are isolated via `pyproject.toml` optional-dependencies (`se3[server]`), so the core CLI is unaffected when they are not installed (see the "Server Modules" Requirement for the specific submodules)
- `se3/` — the SE3 runtime directory (gitignored, except specs/)
  - `specs/` — project specifications (committed to git)
  - `state/` — flow engine state (gitignored), holding various runtime-persisted artifacts:
    - `state/sync_checkpoint.json` — the continuation checkpoint written when `se3 sync` is interrupted (cleared on normal convergence / successful `--resume` completion)
    - `state/sync_state.json` — the persistent incremental cache for `se3 sync` (the "last successful convergence" snapshot), recording the global content fingerprint, whether discovery has converged, each spec's spec_hash and dependency file set, and the obsolete-spec candidate set; written only when sync truly converges with no unresolved failed analyses; unlike `sync_checkpoint.json` — the latter is an interrupt-recovery transient state cleared on convergence, while the former is a build cache that persists across invocations; ignored by the `/se3/*` `.gitignore` rule (a required property: being tracked by git would carry a stale cache across machines and cause a false in-sync determination)
    - `state/engine.json` — the persisted state of the `se3 run` state machine (current step, context, iteration count, etc.), used to support `--resume` continuation after a flow is interrupted
    - `state/test_baseline_cache.json` — the pre-implement test-baseline cache (atomic write, corruption-tolerant), keyed by git HEAD sha + working-tree dirty hash, recording the set of failing test IDs measured at flow start so parallel/resumed flows on the same commit reuse it; used by the flow engine to distinguish newly introduced regressions from inherited (pre-existing) failures (replaces the retired auto-accumulated `state/known_test_failures.json` known-list — see flow-engine *Pre-implement Test Baseline*)
    - `state/baseline_fix_attempts.json` — mechanism B's cross-flow persistent memory (atomic write, corruption-tolerant, schema-versioned, LRU-bounded) of inherited (baseline) test failures the bounded fix loop has *given up* on, keyed per `test_id` with an accumulated attempt count and the latest reason; read so later flows never re-loop a fundamentally un-fixable baseline failure; managed by `engine/baseline_fix_memory.py` and ignored by the `/se3/*` `.gitignore` rule (see flow-engine *Test Step Configuration and Multi-Phase Execution*)
    - `state/merge.lock` — the process-level mutex lock file for `se3 merge` (based on `fcntl.flock` + PID stale detection), preventing concurrent merges
    - `state/summary-*.md` / `state/summary-*.json` — summary snapshots produced at each flow phase (markdown for humans to read, JSON for downstream programs to consume)
    - `state/archive/` — the archive subdirectory for completed or superseded old state files, used for investigating historical flows
  - `cache/` — the cache index
  - `logs/` — execution logs
  - `calls/` — the human-call queue
  - `collab/` — multi-agent collaboration state
  - `history/` — the historical session/flow archive (gitignored), retaining archived artifacts of past `se3 run` / `se3 sync` flows
  - `issues/` — the issue records produced by the issue discovery flow (gitignored), read/written by the issue-discovery-related commands
  - `tmp/` — the temporary-file directory (gitignored), used for flow intermediate artifacts (such as the LLM subprocess's prompt / response snapshots)
  - `worktrees/` — the git worktree workspace directory (gitignored), created and maintained by the worktree-management-related flows to isolate parallel tasks
- `.claude/` — the framework specifications that development depends on (read-only, must not be modified)
- `tests/` — pytest tests
- `scripts/` — helper scripts

### Requirement: Coding Conventions
- Python style follows standard PEP 8
- CLI commands are registered with Typer; complex commands use a sub-typer (`add_typer`), while simple commands with positional arguments use `@app.command`
- Logging uses the `logging` module, with each module declaring `logger = logging.getLogger(__name__)`
- Type annotations use the `from __future__ import annotations` style
- Test files are placed in the `tests/` directory, named `test_*.py`, and use pytest

### Requirement: Key Constraints
- **Bootstrapping constraint**: this project is a bootstrapping project — it both generates new specifications and develops using the published specifications. When generating new specifications, the published specifications under `.claude/` must not be changed
- **Spec read-only**: specs under `se3/specs/` should not be modified arbitrarily during implementation; modifications must pass the spec guardrails check
- **LLM subprocess**: some steps of the flow engine (such as analyze, plan) are executed via an LLM subprocess; these subprocesses cannot access CLAUDE.md and can only obtain project conventions through the spec

### Requirement: Workflow Conventions
- Use `se3 commit` instead of `git commit` (enforces passing tests, intercepts sensitive files)
- Commit messages must include context so the next session can resume easily
- A feature may only be marked complete after tests have been run
- Main entry command: `se3 run "task description"`

### Requirement: CLI Command Modules
Each module under `src/se3/commands/` corresponds to one or a group of `se3` subcommands, registered to the Typer app by `src/se3/cli.py`. New commands must be registered in this spec to prevent the LLM subprocess from being unable to discover command boundaries when CLAUDE.md is absent.

- `run.py` — `se3 run`, the unified entry point for the SE3 3.0 flow engine; replaces the old start/work/done trio of commands and is driven by the state machine; supports creating a new flow, `--resume` continuation, `--loop` loop mode, and `--type=<bugfix|feature>` task-type annotation
- `sync.py` — `se3 sync`, drives `SyncLoop` to perform one-directional code → spec synchronization until convergence; supports switches such as `--once`, `--max-rounds`, `--stable-rounds`, `--interactive`, `--show-diff`, `--resume`, and `--validate-only`; writes only specs, never modifies code; also provides the `process_call_response` entry point for `se3 sync-respond` to handle the human response file for high-risk deletion approvals
- `cli.py::sync_respond_cmd` — `se3 sync-respond <call-file-path>`, handles the human response call file written out by the `se3 sync` flow in scenarios such as the interactive high-impact deletion approval (high-impact deletion call); delegates to `commands/sync.py::process_call_response` to parse the response and advance the sync flow
- `init_cmd.py` — `se3 init`, initializes a new SE3 project; lays down templates such as `se3.yaml`, the base spec, README, `VERSIONS.md`, and the version-management script (registered by `cli.py` via the `@app.command(name="init")` decorator)
- `history_cmd.py` — `se3 history`, viewing and managing session/flow history; subcommands include `list`, `show <flow_id>`, `restore <flow_id>`, and `archived`
- `issue_cmd.py` — `se3 issue`, reading/writing the issue records produced by issue discovery; subcommands include `list` (open-only by default, supports `--all`), `show <id>`, `create` (interactive), and `reset <id>` (resets in-progress back to open)
- `merge_cmd.py` — `se3 merge <branch> [...]`, merges branches sequentially into the current branch; supports `--strategy=default|strict|fast` and `--delete-merged`
- `merge_respond.py` — `se3 merge-respond <call-file-path>`, handles the human/external response files written out via the MCP call queue during the merge flow
- `salvage_cmd.py` — `se3 salvage`, best-effort salvage of work from an abnormally terminated session; fault-tolerantly reads session state, evaluates the git diff, commits existing changes, creates issues for unfinished work, and archives the session, with each step independently fault-tolerant
- `cli.py::guardrails_cmd` — `se3 guardrails`, runs the SE3 Spec Guardrails checks (the spec-format v1 contract, structural constraints, etc.) against the spec files under `se3/specs/`, used to intercept non-compliant spec changes at the commit / sync / CI stages; this command is registered directly in `src/se3/cli.py` via `@app.command(name="guardrails")`, with no separate `commands/guardrails_cmd.py` module file
- `cli.py::daemon_app` — `se3 daemon`, the management subcommand group for the resident control-plane daemon (`start` / `stop` / `status`), registered to `cli.py`'s sub-typer via `add_typer`. `start` launches the daemon as a detached background process by default (`--foreground` keeps it attached to the terminal, `--server-url` specifies the central server address); `stop` stops the running daemon; `status` reports the daemon's running state and tracked flows (`--json` outputs JSON). This command group is defined directly in `src/se3/cli.py`, while the daemon implementation lives in the `src/se3/daemon/` package; imports of the `daemon` package are always deferred into the command body so that core CLI startup is unaffected
- `merge/` — the subpackage of merge-related supporting modules, used by `merge_cmd.py` and `engine/merge/`:
  - `failure_reason.py` — the `FailureReason` IntEnum, replacing the ~60 failure_reason string literals scattered across the old orchestrator, to ease typed dispatch downstream
  - `result_model.py` — the typed result model for the merge orchestrator, split by per-branch outcome (success / failure / skipped), distinguishing `newly_merged` / `already_merged_branches` / `with_warnings`
  - `postcondition.py` — postcondition assertions for the merge success path (three independent conditions: ancestry, merge commit, version bumped)
  - `merge_lock.py` — a process-level merge lock based on `fcntl.flock(LOCK_EX | LOCK_NB)`, preventing concurrent `se3 merge`; non-blocking plus PID-based stale detection
  - `llm_trace.py` — an append-only JSONL trace log of every LLM call during `se3 merge`; each record is `flush`ed after writing (immediately visible via the page cache), but `os.fsync` is changed to batched / reduced-frequency (forced every N records or T seconds by default, and forced on `stop()` / file rotation / process exit) to mitigate the dirty-page write-back IO amplification caused by multiple parallel merge groups streaming trace writes combined with the daemon stat-ing all files every tick; output to `se3/logs/llm/merge_<timestamp>_<seq>.jsonl`
  - `secret_redact.py` — redacts common secret patterns (`sk-...`, `ak-...`, `Bearer <token>`, `ghp_...`, `pypi-...`, `npm_...`, TOML/JSON/YAML password fields, etc.) before writing to the merge log/trace

### Requirement: Agent Runner Abstraction
- Agent execution is unified through the `AgentRunner` abstract base class interface (`src/se3/agent_runner.py`); every concrete runner must implement this interface
- The `InfraErrorType` enum defines the infrastructure error types that require agent rotation: `NONE`, `USAGE_LIMIT`, `TIMEOUT`, `HANG`
- The `RunResult` dataclass represents a runner's execution result, used by the upper-layer flow engine to judge success/failure and rotation decisions
- The only concrete implementation at present is `ClaudeCodeRunner` (`src/se3/claude_runner.py`), wrapping a single Claude Code CLI command invocation; the logic for iterating/rotating the agent command list has been moved up into `LLMCaller`
- On the Linux platform, `psutil` is used for subprocess resource monitoring to detect abnormal states such as hangs
- This abstraction allows new runner types (API-based, other CLI tools, etc.) to be added in the future without changing the upper-layer callers

### Requirement: Engine Module Extensions
Besides the core modules already registered under Directory Structure, `src/se3/engine/` also contains a set of auxiliary/shared modules. New engine modules must be registered in this spec to prevent sub-agents from being unable to discover reusable module boundaries when CLAUDE.md is absent.

- **Spec processing and indexing**
  - `spec_format.py` — the Spec format v1 parser and validator; provides `parse_spec()` (splitting spec markdown into a `ParsedSpec` of a shared header plus a list of `Requirement`s) and `validate()` (v1 rule validation), and defines shared constants such as `SPEC_FORMAT_VERSION_MARKER`
  - `spec_index.py` — an item-level spec index keyed on `<spec>::<requirement>`, tracking mtime / size / sha256 prefix to support incremental invalidation; index file `se3/cache/spec-index.json` (gitignored)
  - `spec_loader.py` — the spec-loading entry point `load_for_step()`, assembling spec text for downstream steps; supports two modes: `items` (full base text + each spec's header + the selected item + 1-hop references) and `full_spec` (full base text + each spec's full text)
- **LLM output structuring**
  - `json_extractor.py` — two-phase JSON extraction: when the main call outputs non-JSON / malformed JSON, a second LLM call re-expresses the content as valid JSON, avoiding polluting the main prompt
  - `json_modes.py` — defines three LLM JSON output strategies: `STRICT` (require_json, retry on failure), `EXTRACT` (json_extract, fall back to LLM extraction on failure), and `TWO_PHASE` (two_phase_json, natural generation + LLM extraction)
  - `schema.py` — the JSON Schema / TypedDict definitions for SE3 state files (`engine.json`, `context.json`, etc.), providing structural documentation and validation capability
- **State, models, and persistence**
  - `models.py` — the core data models of the flow-engine state machine: `Step`, `State`, `Transition`, `FlowInstance`, and enums such as `StepStatus` / `FlowStatus`; fields like `State.fix_history` use a sliding window to control memory and the size of `engine.json`
  - `persistence.py` — JSON serialization/deserialization and atomic writing of flow state such as `engine.json`, preventing state-file corruption from interruptions
  - `context.py` — the `Context` class, providing read-only context for step execution and UI display, encapsulating the workflow state
  - `project_context.py` — the project-level context collector (git status, flow history, backlog, specs, etc.), consumed by the `PROJECT_SUMMARY` step and the `se3 summary` CLI
  - `baseline_fix_memory.py` — mechanism B's cross-flow persistent memory of inherited (baseline) test failures that the bounded fix loop has *given up* on, keyed per `test_id`; provides `load_given_up` / `load_given_up_details` (corruption-tolerant reads, returning an empty set/dict on a missing / corrupt / schema-mismatched store) and `record_given_up` (accumulating the attempt count and latest reason). Persists a schema-versioned JSON document atomically (tempfile + `os.replace`) to `se3/state/baseline_fix_attempts.json` (gitignored under the `/se3/*` rule), bounded to `MAX_ENTRIES` most-recently-touched ids (insertion-order LRU). Prevents every subsequent flow from re-attempting the same un-fixable baseline failure (a missing system library, a flaky test, one needing a human decision); see flow-engine *Test Step Configuration and Multi-Phase Execution*
- **Prompt / retry / history**
  - `retry_context.py` — the shared constants for retry-context formatting (`RETRY_HISTORY_MARKER` / `RETRY_HISTORY_SEPARATOR`, etc.); the producer `chat_history.format_history_for_retry` and the consumer `llm_caller._post_dedup_safety_cap` share the same API; every retry-context block must contain exactly one marker/separator pair
  - `prompt_dedup.py` — the line-level prompt deduplication tool `deduplicate_prompt_lines`, which replaces repeated consecutive line blocks (default `min_block_lines=3`) with a `[DUPLICATED CONTENT: ...]` reference to the first occurrence, reducing prompt size
  - `prompt_markers.py` — centrally defines the three-part sentinel markers separating the "system-instruction boilerplate prefix", the "user literal-input section", and the "framework follow-on injection suffix" within a step prompt (`TEMPLATE_PREFIX_END` / `USER_CONTENT_BEGIN` / `USER_CONTENT_END`, all HTML-comment literals to avoid the LLM echoing them back) and three assembly helpers: `inject_boundary(template, before)` inserts the two-part marker pair (`TEMPLATE_PREFIX_END` + `USER_CONTENT_BEGIN`) once into an existing template string, just before the `before` anchor, idempotently; `wrap_user_content(prefix, content)` directly concatenates the two strings and inserts the two-part marker; `wrap_user_section(prefix, user_content, suffix)` wraps `user_content` between `prefix` and `suffix` using all three markers, producing "prefix + TEMPLATE_PREFIX_END + USER_CONTENT_BEGIN + user_content + USER_CONTENT_END + suffix", idempotently. The core constraint of the three-part semantics is: the user-content section enclosed by `USER_CONTENT_BEGIN` / `USER_CONTENT_END` may contain only "literal input coming from the user" (such as discovery's `initial_description` / `user_response`, interjection.text, etc.); any other string that the se3 framework itself writes (Project Context / Available Specs / Discovery Context wrapper layer / JSON format constraints / Guidelines / language instructions / Runtime Environment injection / READ-ONLY CONSTRAINT, etc.) belongs to the prefix or the suffix. Every step prompt module (analyze / plan / plan_tasks / implement's `IMPLEMENT_PROMPT` / `IMPLEMENT_GROUP_PROMPT` / `FIX_PROMPT` / discovery initial and follow-up / self_check / verify_spec / update_spec / summarize / version_analyze) must call one of these at the template-assembly point: a step with genuine user literal input (currently in practice only discovery) uses `wrap_user_section`, while a step with no user literal input may keep using the two-part marker of `inject_boundary` / `wrap_user_content`. `wrap_user_content` / `inject_boundary` are retained as compatibility entry points; the two-part marker they produce degrades, in frontend recognition, to "prefix + empty user-content + whole suffix". This protocol lets the web running-flow console split a user message into "a system-prefix chip collapsed by default + a user-content bubble expanded by default + a collapsed framework suffix" (see the *Role-Based Message Collapse* requirement of the running-flow-console spec); an old user message with incomplete or missing markers falls back to a single whole chip
  - `prompt_history.py` — interactive prompt history based on `prompt_toolkit` `FileHistory` (default directory `history/`, filename `prompt_history`, `MAX_ENTRIES=500`), supporting up/down arrow browsing of past input
  - `sync_history.py` — a lightweight flow context for the sync flow (`SyncFlowContext`), generating `flow_id` / `step_id` so that `LLMCaller` can automatically record sync's prompt/response through the existing ChatHistory infrastructure
- **Human-interaction call files**
  - `interaction_calls.py` — the unified call-file channel (`se3/calls/`) for every point in a running flow that needs human intervention. Each pending interaction — a pending-response MCP call, a Ctrl-C mid-flight interjection, a retry/failure decision, a CLI subprocess confirmation prompt, the non-interactive discovery confirmation gate (`discovery_confirm`, carrying one-click confirmation `options` whose `value` is `"1"`) — converges into the same kind of `kind`-tagged JSON file (with `kind` drawn from the `CALL_KIND_*` constants in `protocol.py`), carrying display metadata such as `prompt` / `context` / `options` so the daemon aggregator and the web console can render and route without guessing at the text. Provides `write_call` / `read_call` (an old call file lacking the `kind` field defaults to `CALL_KIND_CALL`, preserving backward compatibility) / `read_response` / `write_response`, `write_retry_decision_call` (the no-TTY failure-decision call), `write_interjection_request` (daemon-side interjection writing) / `drain_interjection_requests` (consumed at `se3 run` step boundaries), and `make_cli_confirm_handler` (bridging a CLI subprocess confirmation prompt into a `cli_confirm`-kind call and writing the answer back to the subprocess stdin)
- **Tasks and dependency graph**
  - `task_description.py` — the Task-description composition tool that renders the extra instructions the user entered during a Ctrl-C interruption (persisted in `flow.state.context["user_interjections"]`) into a unified `## Additional Instructions (added during run)` section, guaranteeing that `run.py:_handle_step_interrupt` and `state_machine._build_step_inputs` produce byte-identical output
  - `transitive_reduction.py` — the transitive reduction `transitive_reduce(groups)` of the task-group dependency DAG, removing redundant `depends_on` edges derivable through other paths
  - `stash_utils.py` — shared helper functions for `git stash pop` conflict recovery, shared by the DAG implement step (merging a leaf branch back into the parent worktree) and the `se3 merge` robust strategy (stashing a dirty working tree)
- **Truncation and formatting**
  - `truncation.py` — the shared truncation constants for LLM-consumed content, centrally maintaining the stdout/stderr tail-truncation limits for steps such as `self_check` / `verify_spec` / `test`, ensuring consistency and meeting the lower-bound requirement of the flow-engine spec's "LLM Content Truncation Strategy"
  - `output.py` — the flow engine's core output formatting tool; user-visible content is delegated to `display.py` to render in full (no longer truncated)
  - `output_formatter.py` — the output-formatter registry, centrally registering and looking up formatters by name
  - `display.py` — the full-content rendering tool (based on `rich`), used to display LLM output, spec, proposal, design doc, etc. without truncation
  - `tool_formatters.py` — per-tool `tool_use` / `tool_result` preview formatters based on the `TOOL_FORMATTERS` dict registry, shared by `llm_caller.py` (streaming output) and `chat_history.py` (history review); unknown tools fall back to a generic formatter
  - `step_renderers.py` — the step-output rendering registry, providing the single entry point `render_step_output`, dispatching renderers by step type, with unregistered types using a default generic renderer
  - `logging_config.py` — structured (JSON-format) logging configuration, providing step tracing, latency, and LLM metrics
- **Event stream and pluggable sinks**
  - `event_stream.py` — the unified structured event stream of `se3 run`: defines the `EventType` enum (`flow_started` / `step_started` / `step_output` / `step_completed` / `step_failed` / `flow_paused` / `flow_completed` / `flow_failed` / `interjection_needed` / `call_needed`), the `Event` dataclass, the `new_event` factory function, and the in-process pub/sub emitter `EventEmitter` (`subscribe` / `unsubscribe` / `emit` / `scope`). `se3 run` internally emits only this one stream and is unaware of the caller
  - `sink.py` — pluggable sinks at the end of the event stream: the `Sink` ABC (`consume(event)`) and three concrete implementations — `CliSink` (delegates rendering to the existing `step_renderers.py`, keeping CLI output byte-for-byte compatible; and via `_CLI_SKIP_STEP_TYPES`={`confirm`,`discovery`,`plan`} skips terminal-event rendering for these interactive/special steps, because their CLI output is presented by the orchestrator's interactive/dedicated paths and re-rendering would duplicate output), `JsonSink` (serializes events as NDJSON for consumption in daemon mode), and `HistorySink` (appends `step_completed` events to the per-step jsonl history file, for the daemon `history.py` to report incrementally, from which the web console renders a structured report card expanded by default for each step; the CLI history viewer `chat_history.get_step_history` actively skips such records to avoid duplicate rendering). `HistorySink` is unconditionally subscribed by `src/se3/commands/run.py` in `_run_flow_impl`, unaffected by `--output-format`. The orchestrator now emits a terminal event for **every** step type (including the interactive `confirm`/`discovery`, `plan`, `summarize`) on a terminal result (`COMPLETED`/`PARTIAL`/`FAILED`), so that `HistorySink`/`JsonSink` can persist and forward its structured output; the above `CliSink` skip ensures CLI output is not re-rendered. "CLI vs daemon" degrades to a single `CliSink`/`JsonSink` choice under the outermost `--output-format` switch
- **Subpackages**
  - `formatters/` — the output-formatter subpackage; currently contains concrete formatter implementations such as `task_formatter.py`, registered by `output_formatter.py`
  - `utils/` — the engine-internal generic-utility subpackage; currently contains shared parsing helpers such as `json_parser.py`

### Requirement: Engine Step Implementations
`src/se3/engine/steps/` is the implementation package for each step of the `se3 run` state machine, dispatched by step type by `engine/state_machine.py` as the flow advances. Each step module encapsulates a single flow phase; new steps must be registered in this spec to prevent the LLM subprocess from being unable to discover the available step boundaries and responsibility division when CLAUDE.md is absent.

- `analyze.py` — the analyze step; performs requirements analysis and impact assessment of the user's task, identifies the relevant specs / code modules, and produces the input context for the subsequent plan / implement
- `plan.py` — the plan step; building on analyze, outputs the implementation plan (step breakdown, risk points, verification strategy) as the instruction source for implement
- `plan_tasks.py` — the task-level plan step; further breaks down the overall plan into task groups executable by the DAG scheduler (including `depends_on` dependencies), for `engine/dag_scheduler.py` to schedule
- `implement.py` — the implement step; performs the actual code changes per the plan / plan_tasks output, working with `engine/worktree.py` to complete the implementation inside an isolated worktree
- `verify_spec.py` — the verify_spec step; verifies whether the implementation artifacts satisfy the relevant spec requirements; the truncation strategy for its LLM-consumed content follows the centrally maintained limits in `engine/truncation.py`
- `test.py` — the test step; runs the project test suite and parses the results; stdout/stderr truncation follows the shared limits in `engine/truncation.py`
- `test_with_fail_loop.py` — a test-step variant with a failure loop; on test failure it drives a fix sub-flow and re-runs, constrained by the iteration cap and debouncing of `engine/loop_controller.py`
- `self_check.py` — the self_check step; the agent performs a self-check of the current phase's artifacts; truncation limits are likewise centralized in `engine/truncation.py`
- `_fix_context.py` — a private helper module that builds context (such as failure summaries, historical diffs, etc.) for fix / retry steps; not exposed directly as a step
- `commit.py` — the commit step; invokes logic equivalent to `se3 commit` to land changes; enforces passing tests, intercepts sensitive files, and ensures the commit message contains context
- `confirm.py` — the confirm step; requests confirmation from the user/agent at key junctures (such as approach selection, risk acceptance), collaborating with interaction modules like `engine/sync_interaction.py`
- `discovery.py` — the discovery step; works with `engine/issue_discovery.py` to scan code / spec and produce issue drafts
- `project_summary.py` — the project_summary step; calls `engine/project_context.py` to collect project-level context and produce a summary (also providing the data source for the `se3 summary` CLI)
- `summarize.py` — the summarize step; generates markdown / JSON summary snapshots of the current flow's phase outputs, writing them to `se3/state/summary-*.md` / `summary-*.json`
- `update_spec.py` — the update_spec step; performs controlled updates to the relevant spec files based on implementation / test results; write paths are restricted to `se3/specs/**/spec.md` and are subject to the spec guardrails check
- `spec_gate.py` — the spec_gate step (mechanism A): the post-`update_spec` verification gate inserted between `update_spec` and `version_analyze` in the `feature` / `discovery` sequences; a pure program step (no LLM) that, only when the flow actually changed a spec, first runs the programmatic artifact check (`spec_validator.validate_spec_structure` + a requirement count/name non-decrease check on edited specs relative to the stable pre-`update_spec` snapshot) and then re-runs the full test suite through the shared `steps/test.py::run_and_classify_tests` core; routes back to `update_spec` on an invalid artifact or to `implement` on an introduced test failure; also exports `build_spec_requirement_baseline`, the canonical builder of the pre-`update_spec` spec snapshot shared with the state machine (see flow-engine *Post-update_spec Spec Verification Gate*)
- `version_analyze.py` — the version_analyze step; based on the current flow's commit type (bugfix / feature) and the version baseline from `engine/version_bumper.py`, analyzes and prepares the input needed for the version bump
- `conftest.py` — a pytest configuration file scoped to the `src/se3/engine/steps/` subpackage, used to prevent step implementation modules (especially the one named `test.py` and step files prefixed with `test_`, such as `test_with_fail_loop.py`) from being mistakenly collected by pytest as test cases; this file is not a step implementation but the pytest collection-behavior configuration for this directory, existing as a controlled exception to the Engine Step Implementations constraint that "each step module encapsulates a single flow phase"

### Requirement: Engine Merge Submodules
The `src/se3/engine/merge/` package is the implementation core of the `se3 merge` flow, responsible for orchestrating multi-branch merging, LLM conflict resolution, spec guardrails, runtime data synchronization, and version aggregation into one end-to-end flow. Each submodule has a clear responsibility; new merge submodules must be registered in this spec to prevent the LLM subprocess from being unable to discover the merge flow's module boundaries when CLAUDE.md is absent.

- `orchestrator.py` — `MergeOrchestrator`, the overall orchestration that merges multiple branches sequentially into the current branch: calls `git merge` for each branch, dispatches the clean merge / conflict / non-conflict failure paths, invokes guardrails, and aggregates the per-branch results
- `conflict_context.py` — `ConflictContextBuilder`, collects the three-way merge context for LLM conflict resolution: ours/theirs branch names, the merge-base SHA, HEAD commit info, the four versions of each conflicted file (base/ours/theirs/working tree, including `<<<<<<<` markers), hunk line ranges, the oneline log between base and each side, and spec-file identification; includes magic-byte-signature-based binary-file detection
- `conflict_resolver.py` — `ConflictResolver`, builds a prompt from `ConflictContext` and calls `LLMCaller`, parsing the structured JSON response (resolved content, per-hunk confidence, flags); by default caps resolved file content at 5 MiB to guard against OOM
- `strategy.py` — `StrategyDecider`, the safe/strict/fast three-strategy decision matrix; selects a `DecisionAction` based on the LLM resolution's confidence, the spec guardrail flags, and the file type
- `guardrails.py` — `MergeGuardrailsCheck`, runs guardrails after a merge against the changed spec files under `se3/specs/**/spec.md`, detecting deleted requirements, weakened language, and weakened quantifiers; also exports the reusable pure function `check_spec_diff()` shared with the `se3 guardrails` CLI
- `guardrail_repair.py` — `GuardrailRepairer`, LLM-driven spec repair when guardrails flag a violation under the fast strategy: builds a repair prompt, calls the LLM, parses the corrected content, writes it back to the working tree, commits the repair (preferring a fix-up commit on top of the merge commit, falling back to amend), and re-runs guardrails to verify the repair; all write-back paths are restricted to `se3/specs/**/spec.md`, and `pre_amend_sha` must be saved before amending to support precise rollback
- `human_call.py` — `HumanCallWriter`, when LLM conflict resolution triggers a HUMAN_CALL decision, writes a structured call file to `se3/calls/` containing the conflict context, the LLM resolution, and the decision options for human review (the response file is handled by `se3 merge-respond`)
- `cleanup.py` — `CleanupManager`, implements the `--delete-merged` flag: safely deletes fully merged branches and their bound worktrees with `git branch -d` (lowercase); skips protected branches (main / master / the current branch); refuses to clean up a dirty worktree; runs git subcommands with `LC_ALL=C` to match English stderr; explicitly validates with `git merge-base --is-ancestor` before deletion
- `runtime_sync.py` — runtime data synchronization after a successful merge: the git-ignored runtime data under `se3/` is not automatically merged by git merge, so this module copies the tier A runtime content from the source branch's bound worktree into the current branch's `se3/` directory, and fixes the TOCTOU window of the leaf-symlink swap
- `version_aggregator.py` — after all branches have been merged sequentially, infers the SemVer bump type relative to the merge-base of each branch and the pre-merge HEAD, applies the largest bump to `pyproject.toml`, and amends the last merge commit; includes atomic write-temp + `os.replace` writing, fail-loud on `Version.parse` failure, explicit distinction of `version_already_at_target` (the `VersionNotAdvanced` exception class), a lenient TOML version regex (matching both `version="1.2.3"` and `version = "1.2.3"`), and synchronized restoration of both the pyproject.toml content and the staging area on the failure path

### Requirement: Project Init Templates
- `src/se3/templates/` holds all the template files needed to initialize a new project, used by `se3 init`-type commands when scaffolding a new project

  - directly copied markdown templates (`base_spec.md`, `readme_md.md`, `versions_md.md`) — typically containing placeholder fields such as `{project_name}`, `{project_description}`, `{project_overview}`, `{date}`, which require string-format substitution before use

  - This contract is depended upon by flow modules such as `engine/version_bumper.py`, so the template's output format and exit codes must not be changed without updating the callers
- When adding a file under `templates/`, it must be registered in both this spec and `src/se3/templates/__init__.py` so upper-layer commands can discover and use it
- The current implementation of `src/se3/templates/__init__.py` contains only a single package-level docstring (`"""SE3 templates for project initialization."""`), existing as a Python package marker; it does not yet enumerate the concrete template-file list there via `__all__` / constants / a dict / etc. When adding a template, the registration action must at minimum occur in this spec file; the synchronized registration mechanism in `__init__.py` may be implemented later as actual need arises, but must not conversely weaken the "must be registered" constraint

### Requirement: Daemon Modules

`src/se3/daemon/` is the implementation package for the resident control-plane daemon, driven by the `se3 daemon` subcommand (registered in `cli.py`). The daemon outlives `se3 run` and is the only component that can keep aggregating state and exposing a stable endpoint after the CLI exits. New daemon submodules must be registered in this spec to prevent the LLM subprocess from being unable to discover module boundaries when CLAUDE.md is absent.

- `daemon.py` — the daemon process entry point and lifecycle: `DaemonConfig` (a config dataclass containing `pid_dir`, defaulting to `~/.se3`, overridable via `SE3_DAEMON_DIR`, and storing `daemon.pid` / `daemon_status.json` / `daemon.log` side by side, plus the optional secret `daemon_key` field — the credential the daemon presents in HELLO so the multi-tenant server can resolve it to an owner; it is sourced from `se3 daemon start --daemon-key` or the `SE3_DAEMON_KEY` environment variable, propagated to spawned `se3 run` subprocesses via the `SE3_DAEMON_KEY` child-env var, and never written to the status file or log), `Daemon` (the asyncio event loop), the `start_daemon` / `stop_daemon` / `daemon_status` functions, plus pidfile / status-file management; the `DaemonAlreadyRunning` exception. The machine-local **persistent project-root registry** also lives under `pid_dir` (the `PROJECT_ROOTS_FILENAME` constant → `DaemonConfig.project_roots_file`, e.g. `~/.se3/project_roots.json`), maintained by two helpers: `_read_project_roots(path)` (returns `[]` on missing / corrupt) and `_append_project_root(path, root)` (deduplicates by `realpath`, then atomically writes back via the existing `_atomic_write_json`); being placed under `pid_dir`, it automatically inherits the `SE3_DAEMON_DIR` / `DaemonConfig(pid_dir=...)` override and thereby naturally gains test isolation (tests isolate their writes with `DaemonConfig(pid_dir=tmp_path)` and do not pollute the real `~/.se3`). `Daemon.__init__` injects read / write callbacks based on `config.project_roots_file` (`registry_load` / `registry_persist`) into `DaemonAggregator` (using callbacks rather than a direct import to avoid a top-level aggregator↔daemon circular import), and changes the history reader's `project_roots_provider` from `aggregator.project_roots` (the bare active set) to `aggregator.all_project_roots`, so that `build_index` can still obtain the registry roots and correctly list on-disk history even with zero live processes or after a daemon restart
- `supervisor.py` — `DaemonSupervisor`, discovers and supervises the local `se3 run` processes (via `psutil` scanning and `engine.json` reading), tracking process lifecycle and cleanup
- `spawner.py` — `DaemonSpawner`, spawns new `se3 run --output-format json` subprocesses on others' behalf via `subprocess` (supporting remotely published new tasks), managing their arguments and environment; the `SpawnedProcess` record. It also exposes the `ensure_se3_project(project_root)` hook: it checks whether `<project_root>/se3/specs/base/spec.md` exists; if not, it runs `se3 init -p <project_root>` as a subprocess to complete initialization, and re-validates that the marker file exists after init returns; a failure at any stage is reported back to the caller via a structured `EnsureResult` / equivalent error (`client._handle_spawn` goes straight to the SPAWN_FAILED channel on ensure failure and does not proceed to spawn); when the directory is already an se3 project it is admitted directly, skipping init. Every time `client.py` handles `MSG_SPAWN_FLOW` it must call this hook first, then delegate to the original spawn flow. The argv prefix when spawning an `se3` subprocess is resolved uniformly by the module-level helper `_resolve_se3_command()`, and all spawn paths (`spawn` / `spawn_init` / `spawn_run`) share its result; it is **strictly forbidden** to bypass it and call `shutil.which('se3')` directly or hardcode the `"se3"` literal — the bin directory of the daemon's own Python environment is not necessarily first on PATH (a typical scenario: the daemon runs in `~/.se3-stable` while a pixi/pip environment's bin directory comes earlier on PATH), and resolving by PATH would hit an older se3 console script in another environment, causing cross-version regressions such as the subprocess writing a `se3_version` into `_meta.json` that disagrees with the daemon, the discovery three-part user-content markers being absent, and `StreamJSONTracker` no longer writing `stream_progress` to the jsonl. `_resolve_se3_command()` uses a **same-prefix first** three-level fallback: (1) it prefers `Path(sys.executable).parent / 'se3'` (also probing `se3.exe` on Windows), returning `[<console_script>]` if it exists, guaranteeing the subprocess shares the same Python environment, wheel, and version as the daemon; (2) if the same-prefix one does not exist, it falls back to `[sys.executable, '-m', 'se3']`, reusing the same interpreter to load the `se3` package and avoiding PATH interference; (3) lastly it chooses `shutil.which('se3')` (effective only in extreme packaging scenarios such as a missing `sys.executable`). The return type stays `List[str]` (which may be a single-element `[path]` or `[python, '-m', 'se3']`), so the three call sites need no distinction when concatenating `argv`
- `aggregator.py` — `DaemonAggregator`, polls `se3/state/`, `se3/logs/`, `se3/calls/`, `se3/issues/` and aggregates them into a unified status snapshot (`MachineStatus`); `MachineStatus` also carries `project_roots: List[str]`, which the aggregator, on each snapshot round, merges from four sources via `all_project_roots()`, then deduplicates (normalizing by `realpath`) and stably sorts: (a) the roots actively registered by supervisor / spawner / client through the `_project_roots` set (containing only the active roots discovered / registered within the current process's lifetime, also the source for per-flow snapshot polling), (b) the machine-local **persistent project-root registry** (`DaemonConfig.pid_dir/project_roots.json`, see `daemon.py`) — any "project root that has run se3" is written through to disk via `add_project_root` on any registration path (spawn / ensure / resume / polling discovery, etc.), read back after a daemon restart, independent of live processes (write-through auto-registration: "run it and it's registered", with no pre-configuration needed), (c) all historical `project_root`s that `src/se3/daemon/history.py::enumerate_historical_project_roots()` adds from `se3/history/<flow_id>/_meta.json` and `se3/state/archive/engine_*.json` when it is fed the union "active roots ∪ registry roots", (d) any new root that was init-ed by `ensure_se3_project` before spawn (the client registers it back into `_project_roots` and likewise writes it through the registry via `add_project_root`). `add_project_root`, while adding to the in-memory active set, best-effort writes through to the persistent registry (deduplicated; the I/O is done via the injected `registry_load` / `registry_persist` callbacks), concentrating persistence at a single write-through point rather than scattering it across the four registration call sites, ensuring no registration is missed; `all_project_roots()` is the sole source of this merged view, both producing `MachineStatus.project_roots` via the `_merge_project_roots` delegate and serving as the `project_roots_provider` for the history index's `build_index` (see `daemon.py` / `history.py`), so that even with zero live processes, or after a daemon restart, neither the history list nor the New Task dropdown is empty anymore; per-flow snapshot polling (`get_snapshot`) still uses only the `_project_roots` active set, avoiding polling all historical roots every tick. This field is reported via `STATUS_UPDATE` to drive the Project dropdown of the web New Task form, covering the "active set is empty but historical projects are still usable" scenario after a daemon restart; when enumerating pending-response calls under `se3/calls/`, items that already have a same-named response file (`.response` / `.response.json`) are skipped, to avoid a historically already-answered call being misreported as pending; besides this sibling-response determination, `_enumerate_calls` / `_snapshot_for_root` must also decide whether a pending call is still valid based on the flow's current progress: when a call's owning `context.step_id` is no longer the flow's current step (or that step has already been processed as `COMPLETED` / `REVISION`), the call must be removed from that flow's `pending_calls` even if no `.response` sibling file was written — because interactive calls answered at the CLI terminal (`call` / `cli_confirm` / `discovery_confirm`) are usually consumed directly by the run loop without writing a sibling file, otherwise a stale "awaiting reply" chip would never clear for the whole run; a call still sitting at the current unanswered step stays pending. In addition, for the same `(flow_id, step_id)` only the latest unanswered call is kept (`_dedup_calls_by_step`): discovery's multiple clarification rounds reuse the same `step_id`, writing a new call file each round, and once an old call is superseded by a new round it becomes a stale leftover and must be removed from that flow's `pending_calls` to prevent "awaiting reply" chips from accumulating; a call whose key cannot be located (missing `flow_id` or `step_id`) does not participate in deduplication and is kept as is. Each call file's `kind` field (`call` / `interjection` / `retry_decision` / `cli_confirm`, treated as `call` when absent) is parsed and, together with the `prompt` / `context` / `options` display metadata, enriched into a `PendingCall` and reported via `STATUS_UPDATE`, so the web console can render the various pending interactions differently by `kind`
- `client.py` — `DaemonClient`, maintains one outbound WebSocket connection to the central server (the daemon dials in actively, NAT-friendly), reporting aggregated status, receiving dispatched commands, and routing them to supervisor / spawner; reconnects with exponential backoff after a disconnect; after connecting, reports the historical session index (`MSG_HISTORY_INDEX`), pushes active sessions' historical data in incremental append mode (`MSG_HISTORY_DATA`), handles inbound on-demand history pull requests (`MSG_HISTORY_REQUEST`) by replying with `MSG_HISTORY_DATA`, and handles inbound index re-push requests (`MSG_HISTORY_INDEX_REQUEST`) — upon receipt it calls `_push_history(ws, force_index=True)` to force a rebuild and immediately re-push the latest history index (`force_index=True` bypasses the `engine.json`-change-based debounce so that a waiter suspended on `GET /api/history` at the server end receives the re-push promptly and thereby obtains the latest history rather than a stale last-pushed snapshot); to eliminate the runtime freeze of "the CLI has advanced but the web only sees it at the next status tick", the incremental history push is no longer driven solely by the fixed `status_interval` tick but by `engine.json` changes (detecting an `engine.json` mtime/content change triggers one mtime-debounced push), while the periodic tick is retained as a fallback; `_history_cursors` must advance correctly across ticks / across steps so that step progress of a running flow (including PAUSED/resume) is incrementally reflected to the web within one push cycle; when rebuilding the cursor table from this round's reads each round, for a **terminal flow that has no new records this round but is still an active flow in the current `engine.json`** (typically a flow waiting for `se3 run --resume` after FAILED), its existing cursor must be preserved — otherwise the flow would drop out of the cursor table after the last flush, and when `--resume` later flips the state back to RUNNING the missing cursor would force a full re-read and break the incremental push chain, freezing the web console on the failure snapshot; this preservation is bounded by the active `engine.json` flow set (one per root), so a terminal flow that has been fully read and already archived still drops out normally, keeping the cursor table bounded over the long run; handles inbound `MSG_INTERJECT_FLOW` by writing the mid-flight interjection typed in the web console as the target flow's `interjection`-kind call file, for that `se3 run` process to consume at the next step boundary. **The event loop must not be blocked by synchronous disk I/O**: synchronous calls that do heavy `Path.read_text` / directory traversal / JSON parsing — such as `HistoryReader.read_flow` in `_handle_history_request`, `build_index` in `_push_history` (including the forced rebuild / directory traversal when `force_index=True`), and `read_active_flows` (fanning out to multiple per-step jsonl reads and `json.loads`) — must be executed in a worker thread via `asyncio.to_thread(...)`; the synchronous implementation stays in `daemon/history.py`, and async only wraps a `to_thread` layer at the async entry points in daemon/client.py. This is so that when a session containing a large jsonl is selected, the daemon can still keep responding to PING/PONG, PUSH, and new commands within the window of the server-side `HISTORY_PULL_TIMEOUT` and the client heartbeat timeout (`HEARTBEAT_TIMEOUT`), avoiding the cascading regression of "504 while pulling history, the daemon judged offline at the same time, the machine greying out in the UI, and reconnect backoff triggered"; lightweight probe paths that only `stat` (such as signature scans like `active_flow_signature`) may stay synchronous and need no `to_thread`. When handling `MSG_SPAWN_FLOW`, the client first calls the daemon-internal ensure path (`_handle_ensure_request` → `spawner.ensure_se3_project`): if the target `project_root` is not an existing se3 project, it first runs `se3 init` as a subprocess on the daemon host, and on success registers the root into the aggregator's `_project_roots` before continuing the standard spawn flow; on ensure failure it notifies the server via the existing spawn-failure reporting channel (`SPAWN_FAILED` / equivalent error receipt) and does not enter the spawn phase. For the multi-tenant control plane, `DaemonClient` carries an optional `daemon_key` (empty for local / legacy single-tenant operation) and passes it into `make_hello` so the server can resolve `key → owner_id` and bind this machine to a trust domain; the key lives only in memory and on the HELLO wire and is never logged. On receiving the server's `WELCOME`, the client honours an `accepted=false` rejection (e.g. unknown/invalid daemon key): it records the server-supplied `reason` (which never contains the key), stops replaying the rejected key in a tight reconnect loop, and surfaces a message telling the operator to re-issue / fix the daemon key and restart, rather than hammering the server with a credential it has already rejected (the key is sourced once at daemon startup — see `DaemonConfig.daemon_key` below — and threaded through HELLO only)
- `history.py` — historical session index construction and cursor-based incremental reading: enumerates `se3/history/` and `se3/state/archive/` to build the historical session index (task description, status, time, etc.), distinguishing active / inactive sessions; reads incrementally by per-flow per-step jsonl file cursors, so an active session's conversation records can be reported incrementally without re-sending the whole jsonl each round. While reading, it also parses the authoritative step_type from each per-step jsonl filename (convention `NN_<step_type>_<hash>(_Gk)`) and injects it at the envelope layer, so each reported record looks like `{step_id, step_type, message}`: the raw `message` pushed by the daemon itself does not contain step_type, and after injection the frontend no longer has to guess from the filename, while the `message` content is left untouched to maintain backward compatibility and raw visibility. The parsing is done by the pure function `parse_step_type_from_step_id(stem)` — after stripping the leading `NN_` sequence number, the trailing `_G\d+` group suffix, and the trailing hexadecimal hash segment, it takes the remaining middle segment (which may itself contain underscores, e.g. `version_analyze`) as the step_type, softly validated against the built-in `_KNOWN_STEP_TYPES`; when the naming convention is followed but the type is unregistered it still returns the parsed middle segment (self-describing, drift-tolerant), while an old name with no sequence number and no hash (e.g. `commit_summary`) falls back to the original stem, never raising. The "active" determination of `read_active_flows` must cover **in-progress** flows (including `PAUSED` waiting for user input and the `--resume` continuation state), and must not prematurely drop a flow merely because it is not at the RUNNING terminal value, otherwise the web would freeze during a run and only catch up all at once after archiving; the incremental cursor must advance correctly on each round's read — newly appearing per-step jsonl files and appended lines of the same file must all be taken in, achieving **no loss, no duplication, no truncation of subsequent reads** (a record once read is never re-read, and an unread tail continues next round). It also exports the helper `enumerate_historical_project_roots() -> list[str]`: it traverses `se3/history/<flow_id>/_meta.json` and `se3/state/archive/engine_*.json`, extracts each record's `project_root` field, and deduplicates and sorts them, for `aggregator.py` to merge into `MachineStatus.project_roots` when rebuilding the snapshot; when fed the union "active roots ∪ persistent registry roots" (rather than the active set only), it supplements each root in the union with its on-disk history roots, robustly skipping non-directory / artifact-less roots without raising. The `project_roots_provider` of the history index construction (`build_index`) is injected by the daemon as `aggregator.all_project_roots` (the ordered union of active roots ∪ registry roots ∪ the aforementioned on-disk history roots), replacing the previous approach of directly reading the bare active set `aggregator.project_roots` — the latter is empty when "this machine currently has no se3 run process", which was exactly the root cause of the history list previously always coming up empty (`No history sessions reported.`); after switching to `all_project_roots`, the history index is still non-empty with no live processes, or even after a daemon restart
- `protocol.py` — the single source of truth for the daemon↔server WebSocket protocol: `PROTOCOL_VERSION` (currently `"2"`), `DEFAULT_SERVER_PORT` (the central server's default port `8080`, referenced by both the `--port` default of `se3-server` and the daemon client's URL port completion), the message-type constants (`MSG_HELLO` / `MSG_WELCOME` / `MSG_STATUS_UPDATE` / `MSG_SPAWN_FLOW` / `MSG_RESPOND_CALL` / `MSG_CALL_NOTIFICATION` / `MSG_PING` / `MSG_PONG`, plus the history-related `MSG_HISTORY_INDEX` (daemon→server historical session index) / `MSG_HISTORY_INDEX_REQUEST` (server→daemon, requesting the daemon to rebuild and immediately re-push its historical session index, registered into `SERVER_TO_DAEMON` / `ALL_MESSAGE_TYPES`) / `MSG_HISTORY_REQUEST` (server→daemon, on-demand pull of a historical session's records) / `MSG_HISTORY_DATA` (daemon→server historical-data response, supporting full / append modes and a cursor), plus `MSG_INTERJECT_FLOW` (server→daemon, dispatching one mid-flight interjection typed in the web console to a running flow)) and the `make_*` message constructors (including `make_history_index` / `make_history_index_request` / `make_history_request` / `make_history_data` / `make_interject_flow`; `make_spawn_flow` adds a `discover` field to pass through the "start from discovery" flag). This module also centrally defines the `kind` constants `CALL_KIND_*` (`CALL_KIND_CALL` / `CALL_KIND_INTERJECTION` / `CALL_KIND_RETRY_DECISION` / `CALL_KIND_CLI_CONFIRM`) and the `CALL_KINDS` set for the running-flow human-interaction call files, so that the `kind` value of call files under `se3/calls/` does not drift among the engine, the daemon, and the server. It is imported by both the daemon and the `se3.server` package, ensuring the protocol schema does not drift. A peer encountering an unknown `type` should ignore it, to guarantee that mixed old/new version connections do not crash. For the multi-tenant control plane, `make_hello(machine_id, hostname, se3_version, key="")` carries an **optional** `key` field — the daemon credential the server resolves to an owner (`key → owner_id`) to bind the reporting machine to a trust domain; the field is omitted from the wire when `key` is empty, so a keyless daemon and an older single-tenant server stay wire-compatible (no `PROTOCOL_VERSION` bump), and the key is a secret that MUST NEVER be logged. `make_welcome(server_version, accepted=True, reason="")` carries the `accepted` flag and a (key-free) `reason` string so the server can reject an unauthenticated/invalid-key HELLO with `WELCOME(accepted=false)`

### Requirement: Server Modules

`src/se3/server/` is the standalone package for the central-server backend plus its bundled web frontend; it isolates the heavy web dependencies via `pyproject.toml` optional-dependencies (`se3[server]`) and is launched through the separate console_scripts entry point `se3-server` — not built as a subcommand of the core `se3`. New server submodules must be registered in this spec.

- `app.py` — the FastAPI application entry point: `create_app` assembles the routes, `run` / `main` start it via `uvicorn` and parse `--host` / `--port` / `--version` (`--version` is only a completeness supplement to the argparse help text; the real interception happens in `src/se3/server/__init__.py:main` before FastAPI / uvicorn are imported, with output format `se3-server version {__version__}` aligned with the core `se3 version`); it provides a REST API (machine / flow queries, remotely publishing new tasks, answering pending call/interjection) and mounts `static/` at `/`; `create_app` wires the multi-tenant auth/identity layer **fail-closed**: it constructs the `Store` (sqlite, from `server.db_path`), the `SessionStore`, the `LoginRateLimiter`, the `IdentityService`, and the `ProviderChain` (via `build_provider_chain`, raising `AuthNotConfigured` and refusing to start when no usable provider is configured), and every `/api/*` data route carries `Depends(require_owner)` so an unauthenticated request is rejected with 401; the resolved `OwnerIdentity` is mapped to an owner scope (`_scope_for`) and threaded into the `ServerState` query methods so all machine / flow / history reads are owner-filtered, and `POST /api/flows` / `respond` / `interject` first verify the target machine / flow belongs to the current owner (a foreign target reads as 404), closing the prior identity-unaware remote-command-dispatch hole; the auth surface adds `POST /api/auth/login` (username+password → session cookie), `POST /api/auth/logout`, `GET /api/auth/me` (the current `OwnerIdentity`), and `POST /api/auth/breakglass` (consume a one-time break-glass token → the single stable break-glass admin owner, lazily created via `_ensure_breakglass_admin`); the owner self-service surface adds `POST /api/daemon-keys` (mint a daemon key bound to the current owner, returning the plaintext once), `GET /api/daemon-keys` (list the owner's key metadata), and `DELETE /api/daemon-keys/{key_id}` (revoke); and the admin-gated user-management surface — every route independently enforcing `Depends(require_owner)` + an `is_admin` check (a non-admin caller is rejected 403, before any existence check so the surface leaks nothing) via a shared `create_app`-local `_require_admin` guard, never relying on the frontend hiding the entry — comprises `POST /api/users` (create / invite a local user), `GET /api/users` (list manageable owners as a strict field whitelist — `owner_id` / `display_name` / `is_admin` / `created_at` / identity `provider` / a `can_reset_password` flag — never returning password or daemon-key hashes or any other sensitive field, with the break-glass owner filtered out server-side by reverse-resolving its reserved `(BREAKGLASS_PROVIDER, …)` binding), `DELETE /api/users/{owner_id}` (delete a user, cascading the cleanup of its bindings / credentials / daemon keys via `store.delete_owner` under `ON DELETE CASCADE` foreign keys), `POST /api/users/{owner_id}/password` (reset password — only for `local`-provider owners, reusing `crypto.hash_password` + `store.set_password` with the plaintext hashed off the event loop and never logged; an OIDC / proxy-header owner is refused), and `POST /api/users/{owner_id}/admin` (toggle the `is_admin` flag, reusing the new `store.set_admin`); these mutating routes enforce the non-reversible authorization invariants server-side — the caller may not delete or demote itself, the system's last non-break-glass admin may not be deleted or demoted (the last-admin count-and-write is performed atomically inside `store.delete_owner_guarded` / `store.set_admin_guarded` under a single held lock to close the read-then-write TOCTOU race), the break-glass owner may not be deleted / demoted / password-reset (reading as 404), and an unknown / reserved `owner_id` reads as 404; it includes the history query endpoints `GET /api/history` (the historical session list) and `GET /api/history/{flow_id}` (a session's step conversation records): on every request, `GET /api/history` first broadcasts `MSG_HISTORY_INDEX_REQUEST` to all connected daemons via `broadcast_index_refresh`, waits with a bound for each daemon to force-re-push its latest index (registering/deregistering waiters via `IndexRefreshRegistry`), then aggregates and returns, so that "entering the history list fetches the latest history" without the user manually hard-refreshing; when there is no connected daemon or the wait times out, it robustly degrades to returning the currently cached index (without blocking and without error); `GET /api/history/{flow_id}`, on a cache miss, sends `MSG_HISTORY_REQUEST` to the corresponding daemon and waits for the data to return, with the wait bound controlled by the module-level constant `HISTORY_PULL_TIMEOUT` (currently `30.0` seconds), whose value must be large enough to cover the real disk-read time of a daemon's cold-start first pull of a large session containing several MB of jsonl — even though the daemon already offloads the read to a worker thread as required by `client.py` in *Daemon Modules*, the disk read itself still has appreciable latency, and too narrow a window would return 504 while the daemon is healthy but still reading; it adds the `POST /api/flows/{flow_id}/interject` endpoint, wrapping the mid-flight interjection typed in the web console via `make_interject_flow` into `MSG_INTERJECT_FLOW` and dispatching it to the daemon that owns the flow (fire-and-forget dispatch, returns `202`); it provides the `GET /api/version` endpoint returning `{"version": __version__}`, for the frontend to render the current se3 version number in the top bar, with the version read from the single source `se3.__version__`
- `ws.py` — the WebSocket endpoint: manages the daemon connection pool (connect / disconnect / heartbeat) and the frontend `UiHub` broadcast channel, routing protocol messages (daemon→server status reports, server→daemon command dispatch). For the multi-tenant control plane, the daemon `/ws` HELLO is authenticated fail-closed: the server reads the HELLO `key`, resolves it via `IdentityService.resolve_owner_for_key(key) → owner_id`, binds the machine to that owner (`bind_machine`, setting `MachineRecord.owner_id`), and on a missing / invalid key (or a malformed / non-HELLO opening frame, or a missing `machine_id`) answers `WELCOME(accepted=false, reason=...)` and closes the socket without entering the receive loop. The frontend `/ws/ui` channel is owner-scoped: each UI client is registered in `UiHub` with the `owner_id` it authenticated as (resolved via `require_owner`; an unresolved owner fail-closes the socket), and every push is filtered to that owner's trust domain — `UiHub` precomputes one payload per distinct owner so a client never sees another owner's machines / flows / history; it also routes history messages (`MSG_HISTORY_INDEX` / `MSG_HISTORY_DATA`) by writing them into `ServerState` and broadcasting to `/ws/ui`; and it provides `IndexRefreshRegistry` (registering in-flight index re-push waits by `machine_id`, isomorphic to `HistoryRequestRegistry` but keyed by machine rather than flow) and the `broadcast_index_refresh` helper (dispatching `MSG_HISTORY_INDEX_REQUEST` to each online daemon and registering the corresponding future); upon receiving a daemon's `MSG_HISTORY_INDEX`, besides updating the cache it also resolves the corresponding waiter, so that `GET /api/history` syncs to each daemon's re-pushed latest index before aggregating
- `state.py` — `ServerState`, the in-memory multi-machine / multi-flow aggregated state store. Machine / flow / history live state stays in memory and is rebuilt from daemon reconnects — it is deliberately NOT written to the new sqlite persistence layer (which holds only the identity facts that cannot be reconstructed; see `persistence.py`). `MachineRecord` now also carries an `owner_id` (the trust domain the machine's daemon authenticated as, set when the HELLO key resolves; see `ws.py` / `identity.py`) alongside `project_roots: List[str]`; the machine / flow / history query methods take an `owner` scope argument and filter the returned view so a caller only ever sees machines / flows / history belonging to its own `owner_id`, with a cross-owner machine or flow reading as not-found (404). `update_status` reads `project_roots` from the daemon snapshot and saves it, and `/api/machines` returns this field in the `include_flows=False` overview for frontend linkage; the store additionally caches the historical session index and the already-pulled historical data (purely as in-memory relay / cache, not persisted to disk)
- `persistence.py` — the embedded-sqlite persistence layer: the project's **first** persistence layer (the codebase was previously pure-in-memory — `state.py` historically scoped DB out), introduced as the source of truth for facts that cannot be rebuilt by a daemon reconnecting. It defines the `Store` repository encapsulating all SQL behind a Postgres-swappable interface (callers never see SQL) over exactly five tables: `owners` (the opaque internal `owner_id` primary key + `display_name` + `is_admin`), `identity_bindings` (`(provider, external_id) → owner_id`, one owner may carry many bindings, one external identity maps to one owner), `local_credentials` (the argon2/bcrypt password hash keyed by `owner_id`), `daemon_keys` (issued daemon-key **hashes** bound to an owner), and `breakglass_tokens` (one-time admin break-glass token **hashes**). Beyond the existing `delete_owner` / `set_password` writes, the `Store` adds a `set_admin` update method (`UPDATE owners.is_admin`, returning whether the `owner_id` was hit, same `_lock` + commit + rowcount style as its siblings) backing the admin-toggle route, plus the guarded variants `delete_owner_guarded` / `set_admin_guarded` that perform the last-non-break-glass-admin count-check and the delete / demote write atomically under one held lock. Schema is tracked via `PRAGMA user_version` with an append-only migration list; WAL journal mode + per-thread connections make the single-file DB safe under the server's async + worker-thread access. The DB path comes from `server.db_path` (default `~/.se3/server.db`; `:memory:` for tests). Machine / flow live state is deliberately NOT stored here
- `crypto.py` — the credential-crypto helpers: slow password hashing (`hash_password` / `verify_password`, preferring argon2id via argon2-cffi and falling back to bcrypt), secure random token generation (daemon key / session id / break-glass token), `token_hash` (SHA-256 hashing for at-rest storage of keys/tokens), constant-time comparison (`hmac.compare_digest` / the argon2/bcrypt verifiers), and a redaction helper so credentials never leak into logs
- `identity.py` — the B-layer identity & authorization model, independent of the A-layer provider in use, sitting on top of `Store`: `IdentityService` provides `resolve_owner_for_key(key)` (hash the daemon key, look up its `owner_id`), the in-memory `machine_id → owner_id` index (`bind_machine` / `owner_of_machine` / `unbind_machine`, intentionally NOT persisted because it is live state rebuilt from daemon reconnects), and `link_identity_to_owner` — the cross-provider account-linking **trust gate** seam. Because the owner primary key is the internal `owner_id` (decoupled from any login credential), a future provider switch / addition is just hanging another `(provider, external_id)` binding off an existing `owner_id` (owner_id, the daemon→owner binding, and already-issued daemon keys all stay unchanged, so no daemon re-enrollment). Linking a *new* external identity to an *existing* owner is gated (admin override, or a claim verified on both sides such as a verified email); unverified blind email-equality auto-merge is refused (`UntrustedIdentityLink`) to avoid account takeover under public exposure. v1 only keeps the seam open; the full link UX is left to the second provider
- `auth/` — the pluggable A-layer authentication package (the "resolve the current owner" seam for the human / UI side only; daemons never traverse this layer):
  - `auth/base.py` — the `AuthProvider` ABC (`resolve_owner(request) → OwnerIdentity | None`, where `None` means "cannot authenticate", never "anonymous allowed"), the `OwnerIdentity` dataclass (the stable internal `owner_id` + display name + resolving-provider + `is_admin`), and `ProviderChain` (ordered composition that drops disabled providers and returns the first non-`None` resolution; an empty chain is falsy to drive fail-closed)
  - `auth/local.py` — `LocalAuthProvider`, the default built-in username + password multi-owner authenticator, requiring no external IdP; it owns the login ceremony (verify the local credential hash, establish a session) and is the v1-mandatory authenticator that lets multiple distinct owners be distinguished without an external IdP
  - `auth/session.py` — the server-side session store and `SessionAuthProvider`: `SessionStore` / `Session` plus secure cookie attributes (`CookieConfig` — `HttpOnly` / `Secure` / `SameSite`), shared by every provider whose login ceremony establishes a session; resolution of an established session is provider-agnostic
  - `auth/ratelimit.py` — login failure counting + account lockout (`LoginRateLimiter` / `RateLimitConfig` / `LoginRateLimited`), the brute-force defense for the local provider
  - `auth/registry.py` — `build_provider_chain` assembles the chain from the `server.auth` config (default `["local"]`), constructs each provider and keeps it only if `enabled`, and raises `AuthNotConfigured` (fail-closed) when the resulting chain is empty rather than serving an identity-unaware control plane; `make_require_owner(chain)` builds the `require_owner` FastAPI dependency that resolves every protected request to an `OwnerIdentity` and raises HTTP 401 when nothing resolves (request-boundary fail-closed). FastAPI is imported lazily so the package loads without the `[server]` extra
  - `auth/oidc.py` / `auth/proxy_header.py` — the v1-not-required optional-provider seams (disabled by default): `OidcProvider` (app-internal OIDC social login, `issuer+sub` as `external_id`, standard `state`/`nonce`) and `ProxyHeaderProvider` (read a reverse-proxy-injected trusted identity header — enabling it requires the proxy to strip any client-forged copy of the header and the server to be unreachable bypassing the proxy, else the injected identity is forgeable and it is an authz hole). Both ship only the class skeleton + config validation to keep the schema/seam open
- `bootstrap.py` — break-glass token minting (`issue_breakglass_token`), driven by the `se3-server bootstrap-token` subcommand: it generates a one-time admin token, persists only its SHA-256 hash (`Store.put_breakglass`), and prints the plaintext to the server console exactly once — never stored, never logged. Break-glass is a single admin subject (it never models multiple trust domains — that is the local provider's job), issuance is re-runnable (a fresh token each time, prior tokens stay valid until consumed/purged), and it solves only the two orthogonal problems of first-admin **bootstrap** and a **fail-closed fallback** entrance when the configured provider is unreachable. The module is deliberately dependency-light (only `sqlite3` + crypto helpers, never FastAPI / uvicorn), so the subcommand is intercepted in `server/__init__.py:main` before the `[server]` extra is imported and works on a core-only install
- `static/` — the pure static web frontend (`index.html` / `style.css` / `app.js`), with no build step; receives real-time status over the `/ws/ui` WebSocket and provides an interface to view progress, remotely publish tasks, and respond to interjection/call; the top bar renders a version-number label (`#se3-version`), fetched and displayed via `GET /api/version` on page load; the top bar also carries an admin-only "用户管理" (user-management) entry — gated by a new `admin-only` class (parallel to `auth-only`, switched in `applyAuthState` off `state.identity.is_admin`, since `auth-only` only expresses "logged in") that opens a modal mirroring the daemon-key modal: it lists / creates / deletes users, resets passwords, and toggles admin (`openUsers` / `loadUsers` / `renderUsers` / `createUser` / `deleteUser` / `resetPassword` / `toggleAdmin`), with per-row action availability projected through a testable pure `userRowModel` that disables / hides delete / reset / toggle for the current user, the break-glass owner, and non-`local` providers in lockstep with the server-side guards — the frontend hiding being UX only, never a security boundary; the new-task form provides a "start from the discovery step" option and a linked "Project" dropdown (populated from the selected machine's `project_roots`: 0 items disables submit and shows a hint, 1 item auto-selects, multiple items are required) to ensure `POST /api/flows` is submitted with a non-empty `project_root`; and it provides three history views: the historical session list, a single session's step conversation detail, and the active-session real-time scroll — the empty-list semantics of the history list are split into three class-distinguishable states: (1) `loading-refresh` "Refreshing history…" — shown during each refresh (entering history / the `/api/history` round trip triggered by `fetchHistoryIndex` in flight); (2) `loading-connect` "Connecting / waiting for history data…" — shown continuously while it has not yet confirmed receipt of history data (daemon not connected, or connected but not yet having pushed `history_index` over WS), and does **not** fall back to the empty state just because `/api/history` returns empty-handed within `HISTORY_INDEX_REFRESH_TIMEOUT` (2s) (a daemon connecting and pushing `history_index` often takes about a minute, during which a loading state rather than an empty state must be shown); (3) `empty-confirmed` "No history sessions reported." — shown only once it is truly confirmed (the daemon is connected and zero sessions are confirmed, via a WS-pushed empty `history_index` or a `/api/history` return of a non-empty dataset containing no sessions). The determination logic is extracted into a pure function (e.g. `historyListEmptyState(...)`) so the frontend pure logic can be test-covered; the underlying `broadcast_index_refresh` → daemon `force_index` real-time pull mechanism is unchanged. In the has-sessions branch, the history list is tab-grouped by the `project_root` field each session already carries (entirely based on fields returned by `/api/history`, with no backend change, implemented purely on the frontend within `renderHistoryList()`): a bucket list is derived by deduplicating across sessions (sessions within each bucket retain their original relative order, and buckets are ordered by the time of the newest session in each bucket descending; a session with a missing / empty `project_root` is placed into the "unknown project" bucket corresponding to the internal sentinel constant `UNKNOWN_PROJECT_ROOT` and pinned at the end), a project dropdown (the native `<select class="history-project-select">`) is prepended at the top of `#history-list`, and a selection change (the `change` event) switches `state.historySelectedProjectRoot` and re-renders the list, so the visible set of session cards comes only from the selected bucket; the default-selection strategy is a four-tier fallback "keep the current selection (if it still exists) → the newest session's project_root (i.e. buckets[0]) → the first item → null"; closing the history view (`closeHistory`) resets `state.historySelectedProjectRoot` to `null`, so the next entry re-selects the current active project per the default strategy; the "unknown project" option is rendered only when such legacy sessions actually exist, and when there are fewer than 2 buckets the entire dropdown control is omitted to avoid visual redundancy; the grouping and default selection are extracted into pure functions (e.g. `groupHistorySessionsByProjectRoot` / `pickDefaultHistoryProjectRoot`) so the frontend pure logic can be test-covered. This grouping affects only the historical session list panel and changes neither the New Task form's Project dropdown nor the filtering behavior of the active-session real-time scroll area. A running flow no longer uses the right-side narrow drawer and the separate context-less call-modal popup, but, matching the history view, switches to a full-screen `#flow-view`: the conversation is the scrollable main body area, while Overview / Steps / machine and other auxiliary information are tucked into the sidebar; this view is the sole interaction surface for a running flow, and its behavioral contract is in the `running-flow-console` spec. Entering `#flow-view` pushes a `#flow/<id>` history entry via `history.pushState`, and the close paths (the ✕ button / Escape / the browser back key) all converge onto a single internal close function triggered by `popstate`: ✕ and Escape delegate to `history.back()` to trigger `popstate` in reverse, so the browser back key can close flow-view back to the upper-level list rather than exiting the whole site. The textarea of the docked reply area always stays enabled (briefly disabled only while a submit is in flight), and Send is enabled only when there is a sendable target (a selected chip or an activated interject mode); the Interject button is placed as an inline small icon to the left of the textarea, symmetric with Send, and clicking it toggles interject mode. All conversation records first pass through a unified normalization layer that unwraps the server's `{step_id, step_type, message}` outer wrapper, and it preferentially trusts the envelope-layer authoritative step_type (falling back to the inner `message.step_type`, then to empty) as the source for step dispatch, the step title (`DISCOVERY` etc. rather than the ugly filename `01_discovery_975607bb`), and the report card's type, then groups by step and, within a group, presents a question-and-answer in chronological order with user/assistant/system bubbles; assistant text goes through lightweight Markdown rendering and recognizes inline tool-call markers to render them as separate blocks; over-long records are collapsed by default and can be expanded (on expansion it automatically `scrollIntoView({block:"nearest"})` to scroll the newly appearing content into the viewport, and does not move on collapse); each record provides a "view raw" entry to toggle viewing `raw_json` / `raw_ndjson`

### Requirement: Server Identity, Authentication and Persistence

The central server (`se3.server`) is a multi-tenant control plane: every web/REST request and every daemon connection MUST resolve to an owner trust domain, and authorization MUST be filtered by that owner. The identity-unaware "bare" mode — where any caller could query all machines and `POST /api/flows` to dispatch `se3 run` on any daemon — is removed. This requirement records the structure and invariants of that subsystem (the modules are registered under the *Server Modules* requirement); the configuration surface lives in the `se3-config` *Daemon and Server Configuration* requirement and the CLI surface in the `se3-commands` `se3 daemon` requirement.

**Owner / identity model (B-layer).** An owner is keyed by a stable, opaque internal `owner_id` that is decoupled from every provider's authentication identifier. External / built-in authentication identifiers are mounted as independent `(provider, external_id)` identity-bindings hanging off `owner_id` (a local username, an OIDC `issuer+sub`, a reverse-proxy header email, the reserved break-glass identity, …); one owner MAY carry many bindings, and one `(provider, external_id)` maps to exactly one owner. Because the primary key is `owner_id` rather than any login credential, adding or switching an auth provider in the future is an additive `(provider, external_id)` binding on an existing `owner_id` — `owner_id`, the daemon→owner binding, and already-issued daemon keys all stay unchanged, so daemons need no re-enrollment. Linking a *new* external identity to an *existing* owner MUST pass a trust gate (an admin manual link, or a claim verified on both sides such as a verified email); the server MUST NOT blind-auto-merge on an unverified identity (e.g. unverified email equality) under public exposure (account-takeover risk). v1 only guarantees the schema/seam does not foreclose that path; the link UX is left to the second provider.

**Pluggable authentication (A-layer).** Authentication of the human / UI side flows through a unified `AuthProvider.resolve_owner(request) → OwnerIdentity | None` interface composed into an ordered `ProviderChain`. The default, v1-mandatory provider is the built-in self-managed local authenticator (local accounts + password login + server-side session), which MUST exist because distinguishing multiple trust domains requires a multi-owner authenticator that depends on no external IdP (break-glass, a single subject, cannot serve that role). OIDC social login and a reverse-proxy trusted-header provider are architecturally accommodated but NOT required in v1; they ship as disabled-by-default seams selectable via configuration. When a proxy-header provider is enabled, the reverse proxy MUST strip any client-forged copy of the identity header and the server MUST NOT be reachable bypassing the proxy, otherwise the injected identity is forgeable and it is treated as an authorization hole. Daemons never traverse the A-layer.

**Break-glass bootstrap (orthogonal to provider selection).** A CLI-minted, console-printed, one-time admin token is the single IdP-independent escape hatch, used only for (1) first-admin bootstrap (entering to create accounts / configure a provider) and (2) a fail-closed fallback entrance when the configured provider is unreachable. It is a single admin subject, temporary / re-issuable, stored only as a hash, and never written to logs. Multiple owners are distinguished by the local provider (or an enabled OIDC), never by minting one break-glass token per user.

**Daemon credential issuance.** After login an owner generates / views / revokes their own daemon keys in the UI; the key hash is persisted and bound to that `owner_id`. A daemon presents the key in its HELLO, the server resolves `key → owner_id` and binds the reporting machine to that owner, and the UI / REST views are filtered to the owner. The daemon→server reverse trust is carried by TLS (the daemon dials a known `wss://` address whose server identity is certificate-backed); the application layer does not build a separate server-authentication mechanism, and the server itself does not terminate TLS (a reverse proxy does).

**Persistence boundary.** The server's first persistence layer is an embedded single-file sqlite store (stdlib `sqlite3`, zero external dependency). It persists ONLY the source-of-truth facts that a daemon reconnect cannot rebuild: owner records (keyed by internal `owner_id`), `(provider, external_id) → owner_id` identity-bindings, local password credential hashes, issued daemon-key hashes, and break-glass token hashes. Machine / flow / history real-time state stays in memory and is rebuilt from daemon reconnects. A future Postgres backend is a store-implementation swap behind the same repository interface.

**Security baseline.** Local passwords MUST be stored with a slow hash (argon2 preferred, bcrypt fallback) — never plaintext or a fast hash. Login MUST be rate-limited / lockout-protected against brute force. All credential comparisons MUST be constant-time. Credentials (passwords, sessions, daemon keys, break-glass tokens) MUST NOT be written to logs. The server MUST fail closed: when no usable authentication provider is configured it refuses to serve rather than reverting to the bare mode (`AuthNotConfigured` at startup), and a request that resolves to no owner is rejected with 401. UI session credentials and daemon keys are kept on separate exposure surfaces. When an OIDC provider is enabled, standard `state`/`nonce` validation and secure session attributes MUST hold.

**Channel coverage.** (a) The frontend `/ws/ui` and all `/api/*` REST routes resolve an owner via the provider chain and filter visibility / control by owner — an owner sees only its own machines / flows / history and may `POST /api/flows` / `respond` / `interject` only against its own daemons, with a cross-owner target reading as 404. (b) The daemon `/ws` resolves the HELLO key to an owner and binds the machine; a missing / invalid key is answered with `WELCOME(accepted=false)` and the socket is closed.

**Registration model.** First-boot bootstrap admin plus administrator/operator-provisioned (invited or created) users. v1 does NOT open public self-service registration (its email verification + abuse prevention + password recovery are the heaviest liabilities and there is no mail infrastructure yet); it is left as a future addition.

#### Scenario: Daemon HELLO with a valid key binds the machine to its owner
- **GIVEN** an owner has issued a daemon key (its hash bound to the owner's `owner_id` in the sqlite store)
- **WHEN** a daemon connects to `/ws` and sends HELLO carrying that key
- **THEN** the server resolves `key → owner_id`, binds the machine to that owner (`MachineRecord.owner_id`), and answers `WELCOME(accepted=true)`
- **AND** that machine and its flows are visible only to the owning owner's UI / REST views

#### Scenario: Daemon HELLO with a missing or invalid key is rejected fail-closed
- **WHEN** a daemon connects to `/ws` and sends HELLO with no key, or a key that resolves to no owner
- **THEN** the server answers `WELCOME(accepted=false)` with a key-free reason and closes the socket without entering the receive loop
- **AND** no machine record is bound to any owner for that connection

#### Scenario: REST request without a resolvable owner is rejected
- **WHEN** an `/api/*` data request arrives with no session / credential that the provider chain can resolve to an owner
- **THEN** the request is rejected with HTTP 401 (anonymous access is never admitted)

#### Scenario: Owner cannot see or control another owner's daemon
- **GIVEN** machines `M1` owned by owner `O1` and `M2` owned by owner `O2`
- **WHEN** `O1` lists machines / flows or `POST`s `/api/flows`, `respond`, or `interject` targeting `M2` (or a flow on `M2`)
- **THEN** `O1`'s machine / flow / history views contain only `O1`-owned records
- **AND** the cross-owner target reads as not-found (404) rather than being dispatched

#### Scenario: Server refuses to start when no auth provider is usable
- **GIVEN** the `server.auth` configuration leaves no enabled, usable authentication provider (e.g. local explicitly disabled and no other enabled)
- **WHEN** the server application is assembled
- **THEN** `AuthNotConfigured` is raised and the server refuses to serve — it never falls back to the identity-unaware bare mode

#### Scenario: Local passwords are slow-hashed and never logged
- **WHEN** a local credential is stored
- **THEN** the at-rest value is an argon2 (or bcrypt fallback) slow hash, never plaintext or a fast hash
- **AND** the password, session id, daemon key, and break-glass token never appear in any log line
- **AND** credential verification uses a constant-time comparison

#### Scenario: Break-glass token is one-time, hash-stored, and console-printed
- **WHEN** an operator runs `se3-server bootstrap-token`
- **THEN** a one-time admin token is minted, only its hash is persisted, and the plaintext is printed to the server console exactly once (never logged)
- **AND** consuming it via `POST /api/auth/breakglass` resolves to the single stable break-glass admin owner
- **AND** re-running the command mints a fresh token without invalidating the model's single-admin-subject invariant

#### Scenario: Non-admin is refused on every user-management endpoint
- **GIVEN** an owner whose `OwnerIdentity.is_admin` is false
- **WHEN** it calls any of `GET /api/users`, `DELETE /api/users/{owner_id}`, `POST /api/users/{owner_id}/password`, `POST /api/users/{owner_id}/admin`, or `POST /api/users`
- **THEN** each route independently rejects the request with HTTP 403, and the admin check fires before any existence check so the surface leaks nothing about which owners exist
- **AND** the rejection is enforced server-side — hiding the entry in the frontend is UX only, never the security boundary

#### Scenario: The break-glass owner is excluded from management
- **WHEN** an admin lists users via `GET /api/users`
- **THEN** the owner resolving to the reserved break-glass `(BREAKGLASS_PROVIDER, …)` binding is filtered out of the list server-side
- **AND** any `DELETE` / admin-toggle / password-reset targeting that owner is refused (reading as 404), preserving the single fail-closed escape hatch

#### Scenario: An admin cannot delete or demote itself or the last admin
- **GIVEN** the system's set of non-break-glass admins
- **WHEN** an admin attempts to delete or demote its own `owner_id`
- **THEN** the request is refused
- **AND** **WHEN** deleting or demoting some admin would empty that set (it is the last non-break-glass admin), the request is refused, with the count-check and the delete / demote write performed atomically under one held lock so a concurrent request cannot race past the invariant

#### Scenario: Password reset is restricted to local-provider users
- **WHEN** an admin calls `POST /api/users/{owner_id}/password` for an owner whose identity binding is not `local` (an OIDC or proxy-header source)
- **THEN** the reset is refused server-side (and the frontend hides the action for such users), because `local_credentials` is meaningful only for the local provider
- **AND** for a `local` owner the plaintext password is slow-hashed off the event loop and never written to any log

#### Scenario: Acting on an unknown or reserved owner_id reads as not-found
- **WHEN** a user-management mutation targets an `owner_id` that does not exist (or resolves to a reserved identity)
- **THEN** the request reads as not-found (404) rather than mutating any object

#### Scenario: Adding a second provider does not re-enroll daemons
- **GIVEN** an existing owner with a `(local, <username>)` binding and an already-issued daemon key
- **WHEN** a future provider is added and a new `(provider, external_id)` binding is linked to that same `owner_id` through the trust gate
- **THEN** the `owner_id`, the daemon→owner binding, and the issued daemon key are all unchanged
- **AND** the daemon does not need to be re-keyed or re-enrolled
