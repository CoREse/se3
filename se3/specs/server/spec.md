# server Specification

## Purpose

The standalone central-server backend (`se3-server`) plus bundled web frontend, its multi-tenant identity/auth/persistence model, and the owner-scoped REST/WebSocket surfaces.

## Requirements

### Requirement: Server Modules

`src/se3/server/` is the standalone package for the central-server backend plus its bundled web frontend; it isolates the heavy web dependencies via `pyproject.toml` optional-dependencies (`se3[server]`) and is launched through the separate console_scripts entry point `se3-server` — not built as a subcommand of the core `se3`. New server submodules must be registered in this spec.

- `app.py` — the FastAPI application entry point: `create_app` assembles the routes, `run` / `main` start it via `uvicorn` (the `uvicorn.run` call is given `ws_max_size=protocol.MAX_WS_MESSAGE_BYTES` so the server's inbound frame limit is lifted off uvicorn's 16 MiB default to the shared protocol cap — this is the limit that was silently dropping oversized daemon→server `MSG_HISTORY_DATA` frames and surfacing as a `GET /api/history/{flow_id}` 504) and parse `--host` / `--port` / `--version` (`--version` is only a completeness supplement to the argparse help text; the real interception happens in `src/se3/server/__init__.py:main` before FastAPI / uvicorn are imported, with output format `se3-server version {__version__}` aligned with the core `se3 version`); it provides a REST API (machine / flow queries, remotely publishing new tasks, answering pending call/interjection) and mounts `static/` at `/`; `create_app` wires the multi-tenant auth/identity layer **fail-closed**: it constructs the `Store` (sqlite, from `server.db_path`), the `SessionStore`, the `LoginRateLimiter`, the `IdentityService`, and the `ProviderChain` (via `build_provider_chain`, raising `AuthNotConfigured` and refusing to start when no usable provider is configured), and every `/api/*` data route carries `Depends(require_owner)` so an unauthenticated request is rejected with 401; the resolved `OwnerIdentity` is mapped to an owner scope (`_scope_for`) and threaded into the `ServerState` query methods so all machine / flow / history reads are owner-filtered, and `POST /api/flows` / `respond` / `interject` first verify the target machine / flow belongs to the current owner (a foreign target reads as 404), closing the prior identity-unaware remote-command-dispatch hole; `POST /api/flows` additionally accepts an optional `from_issue_id` parameter (composable with the existing `discover` parameter): when supplied, the server resolves the issue owner-scoped (reusing `ServerState.get_issue_by_id(..., owner=...)`, so an issue on a machine/project outside the caller's owner scope — or an unknown id — reads as 404) to obtain the authoritative target machine/project, then threads `from_issue_id` through `make_spawn_flow` to the owning daemon so the spawned flow is started from that issue (the request's `task_description` being ignored in that case); the auth surface adds `POST /api/auth/login` (username+password → session cookie), `POST /api/auth/logout`, `GET /api/auth/me` (the current `OwnerIdentity`), and `POST /api/auth/breakglass` (consume a one-time break-glass token → the single stable break-glass admin owner, lazily created via `_ensure_breakglass_admin`); the owner self-service surface adds `POST /api/daemon-keys` (mint a daemon key bound to the current owner, returning the plaintext once), `GET /api/daemon-keys` (list the owner's key metadata), and `DELETE /api/daemon-keys/{key_id}` (revoke); and the admin-gated user-management surface — every route independently enforcing `Depends(require_owner)` + an `is_admin` check (a non-admin caller is rejected 403, before any existence check so the surface leaks nothing) via a shared `create_app`-local `_require_admin` guard, never relying on the frontend hiding the entry — comprises `POST /api/users` (create / invite a local user), `GET /api/users` (list manageable owners as a strict field whitelist — `owner_id` / `display_name` / `is_admin` / `created_at` / identity `provider` / a `can_reset_password` flag — never returning password or daemon-key hashes or any other sensitive field, with the break-glass owner filtered out server-side by reverse-resolving its reserved `(BREAKGLASS_PROVIDER, …)` binding), `DELETE /api/users/{owner_id}` (delete a user, cascading the cleanup of its bindings / credentials / daemon keys via `store.delete_owner` under `ON DELETE CASCADE` foreign keys), `POST /api/users/{owner_id}/password` (reset password — only for `local`-provider owners, reusing `crypto.hash_password` + `store.set_password` with the plaintext hashed off the event loop and never logged; an OIDC / proxy-header owner is refused), and `POST /api/users/{owner_id}/admin` (toggle the `is_admin` flag, reusing the new `store.set_admin`); these mutating routes enforce the non-reversible authorization invariants server-side — the caller may not delete or demote itself, the system's last non-break-glass admin may not be deleted or demoted (the last-admin count-and-write is performed atomically inside `store.delete_owner_guarded` / `store.set_admin_guarded` under a single held lock to close the read-then-write TOCTOU race), the break-glass owner may not be deleted / demoted / password-reset (reading as 404), and an unknown / reserved `owner_id` reads as 404; it includes the history query endpoints `GET /api/history` (the historical session list) and `GET /api/history/{flow_id}` (a session's step conversation records): on every request, `GET /api/history` first broadcasts `MSG_HISTORY_INDEX_REQUEST` to all connected daemons via `broadcast_index_refresh`, waits with a bound for each daemon to force-re-push its latest index (registering/deregistering waiters via `IndexRefreshRegistry`), then aggregates and returns, so that "entering the history list fetches the latest history" without the user manually hard-refreshing; when there is no connected daemon or the wait times out, it robustly degrades to returning the currently cached index (without blocking and without error); `GET /api/history/{flow_id}`, on a cache miss, before dispatching the on-demand pull MUST resolve the flow's **authoritative `project_root`** via the new `ServerState.get_history_flow_project_root(flow_id, owner=...)` — the root recorded in that flow's `SessionMeta.project_root` — and thread it (via the existing `request_history` → `make_history_request` `project_root` parameter) into the `MSG_HISTORY_REQUEST` sent to the corresponding daemon, then waits for the data to return, with the wait bound controlled by the module-level constant `HISTORY_PULL_TIMEOUT` (currently `30.0` seconds). Passing the authoritative root makes that root the **single source of truth** the daemon reads from (and merges across — see the `daemon` *Daemon Modules* multi-root merge read resolution) rather than letting the daemon guess by scanning its project-root registry and taking the first root that happens to contain `se3/history/<flow_id>/`. This is the direct trigger fix for the worktree-mode symptom where the WebUI only showed the first (discovery) step: a worktree flow runs discovery in the main repo root and every later step under the worktree root, so two roots each hold a `se3/history/<flow_id>` directory and the daemon's first-match heuristic returned the discovery-only main repo. Resolution degrades gracefully — when the flow is unknown / owner-scoped out / has no recorded root, `get_history_flow_project_root` returns `None` and the pull falls back to the legacy empty-`project_root` behaviour, so an ordinary non-worktree pull is unaffected. `HISTORY_PULL_TIMEOUT`'s value must be large enough to cover the real disk-read time of a daemon's cold-start first pull of a large session containing several MB of jsonl — even though the daemon already offloads the read to a worker thread as required by `client.py` in *Daemon Modules*, the disk read itself still has appreciable latency, and too narrow a window would return 504 while the daemon is healthy but still reading; `GET /api/history/{flow_id}` additionally accepts an optional `after` query parameter carrying an **opaque progress token** the client echoes on a WebSocket-reconnect re-fetch so the server can return only the records that accrued during the outage instead of the whole bundle: every response carries a `delivery` field (`"delta"` or `"full"`) and a fresh `progress` token, the token is produced and validated inside `state.py` (see `ServerState`), and the route serves a delta **only** on a cache hit whose bundle still pins the echoed token — every unsafe case (a missing / malformed / tampered token, a generation mismatch from a `mode: full` cache replacement, a machine / owner change, or a cache miss that pulls fresh records from the daemon) falls back to returning the full record list with `delivery: "full"` and a new token; the existing owner / ownership validation (`require_owner`, `find_machine_for_history_flow`) and the cache-miss daemon-pull semantics are unchanged by the incremental path; it adds the `POST /api/flows/{flow_id}/interject` endpoint, wrapping the mid-flight interjection typed in the web console via `make_interject_flow` into `MSG_INTERJECT_FLOW` and dispatching it to the daemon that owns the flow (fire-and-forget dispatch, returns `202`); it provides the `GET /api/version` endpoint returning `{"version": __version__}`, for the frontend to render the current se3 version number in the top bar, with the version read from the single source `se3.__version__`; it adds the **flow resume** endpoint `POST /api/flows/{flow_id}/resume`, which **pre-validates before returning any optimistic receipt** rather than unconditionally answering `resume_dispatched`. It first resolves the flow owner-scoped via `ServerState.get_flow`: an unknown / cross-owner flow (or one on a disconnected machine) maps to `404 not found`. A resolved flow is then split on `ServerState.is_flow_resumable` — the authoritative `resumable` decision the daemon already gated by the live-process rule (see the `daemon` *Daemon Modules* live-process resumable gate), so a `RUNNING` flow whose project root still holds a live process is **not** resumable here either. Only a genuinely resumable flow (`FAILED` / `PAUSED`, or a `RUNNING`-but-dead interrupted flow) dispatches a `MSG_SPAWN_FLOW` carrying `resume_flow_id` to the owning daemon and returns `202 resume_dispatched`. A resolved-but-not-resumable flow returns `409` (never a misleading `dispatched`), split by status so the user sees *why*: a still-running flow (a running/init/recovering status whose live process gated `resumable` to `False`) returns `409` with the explicit detail "该 flow 仍在运行，无法 resume", and a normally `COMPLETED` flow returns `409` with "已完成，无法 resume". This keeps the receipt honest — the optimistic `resume_dispatched` is emitted **only** when a resume was actually dispatched, so a user is never told a re-spawn was triggered against a flow that is still live. The daemon's `request_resume` live-process guard remains the final backstop behind this visible, user-facing rejection; it adds the **flow end-session** endpoint `POST /api/flows/{flow_id}/end` (an `EndSessionRequest` body carrying an optional `reason`), which actively terminates a session and — for a worktree session — archives it without merging its work back. Like resume it carries `Depends(require_owner)` and resolves the flow owner-scoped via `ServerState.get_flow`: an unknown / cross-owner flow maps to `404`. It is then state-pre-validated via the `ServerState.is_flow_endable` helper — a `COMPLETED` flow is already finished and reads `409` (nothing to end). A disconnected owning machine reads `503`. Only an endable flow on a connected daemon dispatches a `make_end_session` (→ `MSG_END_SESSION`) to the owning daemon via `manager.send_to` and returns `202 end_dispatched`. Unlike resume it deliberately admits non-completed flows in **any** active / recoverable status (`RUNNING` / `PAUSED` / `FAILED` / `RECOVERING` / `INIT`), because a dangling worktree may originate from a still-running, paused, or failed session; the dispatch is fire-and-forget (no `MSG_END_RESULT` ack), with the flow's termination + archival reflected by the next `STATUS_UPDATE`; and it adds the **owner-scoped issue-management REST surface** mirroring each daemon's on-disk issues from the `STATUS_UPDATE` snapshot: `GET /api/issues` (list across the owner's machines, optionally filtered by `machine_id` / `project_root` / `include_closed` / `source` / `type`), `GET /api/issues/{issue_id}` (single issue), `POST /api/issues` (create — `description` required, other fields optional, written with `source="human"`), `PATCH /api/issues/{issue_id}` (edit), `POST /api/issues/{issue_id}/close` (with optional `reason`), and `POST /api/issues/{issue_id}/reopen`. The four write routes resolve the owning machine from the issue mirror, dispatch a `protocol.make_issue_command` (`create` / `edit` / `close` / `reopen`) to that daemon, and await the correlated `MSG_ISSUE_RESULT` via an `IssueCommandRegistry` (bounded by the short per-operation `ISSUE_COMMAND_TIMEOUT`, currently `10.0` seconds). On an ack timeout the route MUST NOT immediately report failure: because the daemon may already have persisted the issue with only the ack delayed (e.g. behind a heavy daemon-side snapshot racing the periodic pushes), `_send_issue_command` falls back to a bounded **reconcile** window (`_reconcile_issue_command`, bounded by `ISSUE_RECONCILE_TIMEOUT`, currently `15.0` seconds, polling every `ISSUE_RECONCILE_POLL_INTERVAL`, currently `0.5` seconds) that checks the operation's expected post-condition against the in-memory issue mirror (refreshed by `STATUS_UPDATE`): `create` looks for a new `source="human"` issue under the target `project_root` whose id is absent from the pre-send baseline id set (snapshotted before dispatch, since the daemon — not the server — allocates the new id), while `edit` / `close` / `reopen` key off the known `target_issue_id` and confirm the expected field updates / a no-longer-open(in-progress) status / a reopened-open status respectively. If reconcile observes the post-condition it corrects the result to success (returning the affected `issue_id` with `reconciled=True`) so the front end sees a created/succeeded outcome instead of a spurious red failure for an issue that already landed on disk; only if the reconcile window also elapses with the change still absent does the route return failure. The reconcile fallback triggers **only** on the ack `TimeoutError`, so it never masks a genuine daemon-reported failure (an explicit `ok=false` ack still surfaces as failure). The reconcile path reuses the existing in-memory mirror (`state.get_issues` / `state.get_issue_by_id`) and adds no server-side disk read, preserving the architecture boundary that the daemon is the only issue-persistence edge. Like the other data routes every issue route carries `Depends(require_owner)` and only ever sees issues on the caller's own machines (a foreign machine/issue reads as `404`)
- `ws.py` — the WebSocket endpoint: manages the daemon connection pool (connect / disconnect / heartbeat) and the frontend `UiHub` broadcast channel, routing protocol messages (daemon→server status reports, server→daemon command dispatch). For the multi-tenant control plane, the daemon `/ws` HELLO is authenticated fail-closed: the server reads the HELLO `key`, resolves it via `IdentityService.resolve_owner_for_key(key) → owner_id`, binds the machine to that owner (`bind_machine`, setting `MachineRecord.owner_id`), and on a missing / invalid key (or a malformed / non-HELLO opening frame, or a missing `machine_id`) answers `WELCOME(accepted=false, reason=...)` and closes the socket without entering the receive loop. The frontend `/ws/ui` channel is owner-scoped: each UI client is registered in `UiHub` with the `owner_id` it authenticated as (resolved via `require_owner`; an unresolved owner fail-closes the socket), and every push is filtered to that owner's trust domain — `UiHub` precomputes one payload per distinct owner so a client never sees another owner's machines / flows / history; it also routes history messages (`MSG_HISTORY_INDEX` / `MSG_HISTORY_DATA`) by writing them into `ServerState` and broadcasting to `/ws/ui`. When a `MSG_HISTORY_DATA` frame resolves a pending REST pull waiter (`HistoryRequestRegistry`, the cache-miss `GET /api/history/{flow_id}` path), the `/ws/ui` broadcast MUST be suppressed **only** for a `mode: full` response — that is, the suppression predicate is `suppress_broadcast = resolved_pull and mode == protocol.HISTORY_MODE_FULL`, not the broader "any frame that resolved a pull waiter": suppression exists to keep a cache-miss full pull (whose synchronous REST reply already carries the complete bundle and whose `mode: full` push would otherwise clear every subscriber's progress token) from being re-broadcast to all clients; a `mode: append` real-time increment, by contrast, MUST ALWAYS be broadcast to the owner's `/ws/ui` clients even when that same frame happens to also resolve a pending pull waiter, so that the records that accrue after a `respond` / `interject` keep appending in any already-subscribed running-flow live view without the user having to leave and re-enter the view to trigger a fresh `/api/history` full snapshot. The REST-pull-initiating client deduplicates the doubly-delivered append (REST response plus WS broadcast) via the frontend `dedupeAppendRecords` (see `running-flow-console::Live-Append Record Deduplication Against Snapshot`), so an always-broadcast append never renders twice. And it provides `IndexRefreshRegistry` (registering in-flight index re-push waits by `machine_id`, isomorphic to `HistoryRequestRegistry` but keyed by machine rather than flow) and the `broadcast_index_refresh` helper (dispatching `MSG_HISTORY_INDEX_REQUEST` to each online daemon and registering the corresponding future); upon receiving a daemon's `MSG_HISTORY_INDEX`, besides updating the cache it also resolves the corresponding waiter, so that `GET /api/history` syncs to each daemon's re-pushed latest index before aggregating; and it routes a daemon's `MSG_ISSUE_RESULT` by resolving the matching `IssueCommandRegistry` waiter keyed by `request_id`, so the awaiting issue REST handler can return the daemon's `ok` / `error` acknowledgment; and it routes a daemon's `MSG_SPAWN_FAILED` — sent when a spawn/init genuinely fails on the daemon host (e.g. an `ensure_se3_project` init failure, where `client._handle_spawn` no longer silently returns) — by translating it into a `UI_EVENT_SPAWN_FAILED` frame (carrying the originating `machine_id` / `project_root` / `error` plus, when present, `task_description` / `from_issue_id` / `resume_flow_id`) and broadcasting it to that owner's `/ws/ui` clients, so the web console flips the just-published task from a "published" state to a visible error rather than leaving it silently stuck
- `state.py` — `ServerState`, the in-memory multi-machine / multi-flow aggregated state store. Machine / flow / history live state stays in memory and is rebuilt from daemon reconnects — it is deliberately NOT written to the new sqlite persistence layer (which holds only the identity facts that cannot be reconstructed; see `persistence.py`). `MachineRecord` now also carries an `owner_id` (the trust domain the machine's daemon authenticated as, set when the HELLO key resolves; see `ws.py` / `identity.py`) alongside `project_roots: List[str]`; the machine / flow / history query methods take an `owner` scope argument and filter the returned view so a caller only ever sees machines / flows / history belonging to its own `owner_id`, with a cross-owner machine or flow reading as not-found (404). `update_status` reads `project_roots` from the daemon snapshot and saves it, and `/api/machines` returns this field in the `include_flows=False` overview for frontend linkage; the store additionally caches the historical session index and the already-pulled historical data (purely as in-memory relay / cache, not persisted to disk). Each cached history bundle also carries an in-memory `generation` lifecycle id (handed out fresh whenever the bundle is first built or replaced by a `mode: full` push, kept stable across ordinary `append` pushes). **Old-format (generation-less) bundle backward compatibility:** a bundle produced before the `generation` field existed is back-filled with a stable positive `generation` on first contact (via a shared `_ensure_generation` helper applied in both `get_history` and `get_history_snapshot`, and in the `append`-extend path so an append on a legacy bundle also carries a `generation`), so a generation-less old session participates in token validation as a first-class value and is served via the **delta** path instead of being forced into a permanent full-reload fallback (the prior bug: an old bundle's missing `generation` read as `0`, never matched a progress token's `generation` (≥1), and so always fell back to full). On a delta, the offset is clamped to `[0, total]`; any full fallback always returns the **complete** record set so the delivered records equal the on-disk jsonl in full regardless of delivery mode. `state.py` provides the `encode_progress` / `decode_progress` helpers that mint and validate the **opaque, HMAC-signed progress token** echoed by `GET /api/history/{flow_id}`'s `after` parameter, binding `(generation, offset, machine_id)` so a token issued before an append still validates while a token issued against a since-replaced bundle does not. The history-snapshot read method serves the delta tail and the full record list atomically under the same lock — it validates the echoed token against the current bundle and expected machine, returns the records after the token's `offset` with `delivery: "delta"` when the token still pins the bundle, and returns the full records with `delivery: "full"` (plus a new token) on every fallback (no token, stale / mismatched generation, machine / owner change, or cache miss); the token is content-free (it carries no record bodies) and signed so a client cannot forge or advance the offset and silently skip records. `update_status` also ingests the snapshot's `issues` list into a per-machine, per-`project_root` issue mirror (`_issues`), and `ServerState` exposes owner-scoped `get_issues(...)` (with `machine_id` / `project_root` / `include_closed` / `source` / `type_filter` filters) and `get_issue_by_id(...)` over that mirror, plus `is_flow_resumable(flow_id, owner=...)` which returns the `(machine_id, flow)` pair when the flow is owner-visible and is resumable — **primarily** when the flow's authoritative `resumable` flag is true (computed by the daemon from the flow's semantic state and threaded through `FlowSnapshot.resumable` via `from_payload` / `to_dict` so the daemon-injected per-flow resumable snapshots, see the daemon *Daemon Modules* requirement, surface here), with a **backward-compatible fallback** to its status being in `RESUMABLE_STATUSES` (`{failed, paused}`) for flag-less payloads — the in-memory authority behind the issue REST surface and the `POST /api/flows/{id}/resume` gate; it likewise exposes `is_flow_endable(flow_id, owner=...)`, which returns the `(machine_id, flow)` pair when the flow is owner-visible and is **not** already `COMPLETED` — the gate behind `POST /api/flows/{id}/end`, deliberately broader than `is_flow_resumable` because a dangling worktree to clean up may belong to a still-running, paused, or failed session. `ServerState` also exposes the owner-scoped `get_history_flow_project_root(flow_id, owner=...)`, which resolves the **authoritative `project_root`** a flow runs under so the cache-miss history pull (`app.py`'s `GET /api/history/{flow_id}`) can tell the daemon *which* root to read instead of letting it guess by first-match registry scan. Resolution is owner-scoped and tried in order: (1) the reported history index, whose `SessionMeta` carries the authoritative `project_root` of each flow's run; then (2) the live flow set, for an active flow not yet indexed. It returns the non-empty `project_root` string, or `None` when the flow is unknown, owner-scoped out, or has no recorded root (the caller then degrades to the legacy empty-`project_root` behaviour). This is the in-memory single source of truth that fixes the worktree-mode history-read bug where a flow's discovery step (main repo root) and later steps (worktree root) live under two distinct roots, so the daemon's first-match heuristic returned only the discovery-only main repo. The issue mirror, like all machine/flow/history live state, is rebuilt from daemon snapshots and deliberately NOT persisted to sqlite
- `persistence.py` — the embedded-sqlite persistence layer: the project's **first** persistence layer (the codebase was previously pure-in-memory — `state.py` historically scoped DB out), introduced as the source of truth for facts that cannot be rebuilt by a daemon reconnecting. It defines the `Store` repository encapsulating all SQL behind a Postgres-swappable interface (callers never see SQL) over exactly five tables: `owners` (the opaque internal `owner_id` primary key + `display_name` + `is_admin`), `identity_bindings` (`(provider, external_id) → owner_id`, one owner may carry many bindings, one external identity maps to one owner), `local_credentials` (the argon2/bcrypt password hash keyed by `owner_id`), `daemon_keys` (issued daemon-key **hashes** bound to an owner), and `breakglass_tokens` (one-time admin break-glass token **hashes**). Beyond the existing `delete_owner` / `set_password` writes, the `Store` adds a `set_admin` update method (`UPDATE owners.is_admin`, returning whether the `owner_id` was hit, same `_lock` + commit + rowcount style as its siblings) backing the admin-toggle route, plus the guarded variants `delete_owner_guarded` / `set_admin_guarded` that perform the last-non-break-glass-admin count-check and the delete / demote write atomically under one held lock. Schema is tracked via `PRAGMA user_version` with an append-only migration list; WAL journal mode + per-thread connections make the single-file DB safe under the server's async + worker-thread access. The DB path comes from `server.db_path` (default `~/.se3/server.db`; `:memory:` for tests). Machine / flow live state is deliberately NOT stored here
- `crypto.py` — the credential-crypto helpers: slow password hashing (`hash_password` / `verify_password`, preferring argon2id via argon2-cffi and falling back to bcrypt), secure random token generation (daemon key / session id / break-glass token), `token_hash` (SHA-256 hashing for at-rest storage of keys/tokens), constant-time comparison (`hmac.compare_digest` / the argon2/bcrypt verifiers), and a redaction helper so credentials never leak into logs
- `identity.py` — the B-layer identity & authorization model, independent of the A-layer provider in use, sitting on top of `Store`: `IdentityService` provides `resolve_owner_for_key(key)` (hash the daemon key, look up its `owner_id`), the in-memory `machine_id → owner_id` index (`bind_machine` / `owner_of_machine` / `unbind_machine`, intentionally NOT persisted because it is live state rebuilt from daemon reconnects), and `link_identity_to_owner` — the cross-provider account-linking **trust gate** seam. Because the owner primary key is the internal `owner_id` (decoupled from any login credential), a future provider switch / addition is just hanging another `(provider, external_id)` binding off an existing `owner_id` (owner_id, the daemon→owner binding, and already-issued daemon keys all stay unchanged, so no daemon re-enrollment). Linking a *new* external identity to an *existing* owner is gated (admin override, or a claim verified on both sides such as a verified email); unverified blind email-equality auto-merge is refused (`UntrustedIdentityLink`) to avoid account takeover under public exposure. v1 only keeps the seam open; the full link UX is left to the second provider
- `auth/` — the pluggable A-layer authentication package (the "resolve the current owner" seam for the human / UI side only; daemons never traverse this layer):
  - `auth/base.py` — the `AuthProvider` ABC (`resolve_owner(request) → OwnerIdentity | None`, where `None` means "cannot authenticate", never "anonymous allowed"), the `OwnerIdentity` dataclass (the stable internal `owner_id` + display name + resolving-provider + `is_admin`), and `ProviderChain` (ordered composition that drops disabled providers and returns the first non-`None` resolution; an empty chain is falsy to drive fail-closed)
  - `auth/local.py` — `LocalAuthProvider`, the default built-in username + password multi-owner authenticator, requiring no external IdP; it owns the login ceremony (verify the local credential hash, establish a session) and is the v1-mandatory authenticator that lets multiple distinct owners be distinguished without an external IdP
  - `auth/session.py` — the server-side session store and `SessionAuthProvider`: `SessionStore` / `Session` plus secure cookie attributes (`CookieConfig` — `HttpOnly` / `Secure` / `SameSite`), shared by every provider whose login ceremony establishes a session; resolution of an established session is provider-agnostic
  - `auth/ratelimit.py` — login failure counting + account lockout (`LoginRateLimiter` / `RateLimitConfig` / `LoginRateLimited`), the brute-force defense for the local provider
  - `auth/registry.py` — `build_provider_chain` assembles the chain from the `server.auth` config (default `["local"]`), constructs each provider and keeps it only if `enabled`, and raises `AuthNotConfigured` (fail-closed) when the resulting chain is empty rather than serving an identity-unaware control plane; `make_require_owner(chain)` builds the `require_owner` FastAPI dependency that resolves every protected request to an `OwnerIdentity` and raises HTTP 401 when nothing resolves (request-boundary fail-closed). FastAPI is imported lazily so the package loads without the `[server]` extra
  - `auth/oidc.py` / `auth/proxy_header.py` — the v1-not-required optional-provider seams (disabled by default): `OidcProvider` (app-internal OIDC social login, `issuer+sub` as `external_id`, standard `state`/`nonce`) and `ProxyHeaderProvider` (read a reverse-proxy-injected trusted identity header — enabling it requires the proxy to strip any client-forged copy of the header and the server to be unreachable bypassing the proxy, else the injected identity is forgeable and it is an authz hole). Both ship only the class skeleton + config validation to keep the schema/seam open
- `bootstrap.py` — break-glass token minting (`issue_breakglass_token`), driven by the `se3-server bootstrap-token` subcommand: it generates a one-time admin token, persists only its SHA-256 hash (`Store.put_breakglass`), and prints the plaintext to the server console exactly once — never stored, never logged. - **THEN** the server's `ws.py` translates it into a `UI_EVENT_SPAWN_FAILED` frame (with `machine_id` / `project_root` / `error`, plus `task_description` / `from_issue_id` / `resume_flow_id` when present) and broadcasts it only to that owner's `/ws/ui` clients
- **AND** the web console flips the just-published task from "published" to a visible error state instead of leaving it silently stuck

### Requirement: Server Identity, Authentication and Persistence

The central server (`se3.server`) is a multi-tenant control plane: every web/REST request and every daemon connection MUST resolve to an owner trust domain, and authorization MUST be filtered by that owner. The identity-unaware "bare" mode — where any caller could query all machines and `POST /api/flows` to dispatch `se3 run` on any daemon — is removed. This requirement records the structure and invariants of that subsystem (the modules are registered under the *Server Modules* requirement); the configuration surface lives in the `se3-config` *Daemon and Server Configuration* requirement and the CLI surface in the `se3-commands` `se3 daemon` requirement.

**Owner / identity model (B-layer).** An owner is keyed by a stable, opaque internal `owner_id` that is decoupled from every provider's authentication identifier. External / built-in authentication identifiers are mounted as independent `(provider, external_id)` identity-bindings hanging off `owner_id` (a local username, an OIDC `issuer+sub`, a reverse-proxy header email, the reserved break-glass identity, …); one owner MAY carry many bindings, and one `(provider, external_id)` maps to exactly one owner. Because the primary key is `owner_id` rather than any login credential, adding or switching an auth provider in the future is an additive `(provider, external_id)` binding on an existing `owner_id` — `owner_id`, the daemon→owner binding, and already-issued daemon keys all stay unchanged, so daemons need no re-enrollment. Linking a *new* external identity to an *existing* owner MUST pass a trust gate (an admin manual link, or a claim verified on both sides such as a verified email); the server MUST NOT blind-auto-merge on an unverified identity (e.g. unverified email equality) under public exposure (account-takeover risk). v1 only guarantees the schema/seam does not foreclose that path; the link UX is left to the second provider.

**Pluggable authentication (A-layer).** Authentication of the human / UI side flows through a unified `AuthProvider.resolve_owner(request) → OwnerIdentity | None` interface composed into an ordered `ProviderChain`. The default, v1-mandatory provider is the built-in self-managed local authenticator (local accounts + password login + server-side session), which MUST exist because distinguishing multiple trust domains requires a multi-owner authenticator that depends on no external IdP (break-glass, a single subject, cannot serve that role). OIDC social login and a reverse-proxy trusted-header provider are architecturally accommodated but NOT required in v1; they ship as disabled-by-default seams selectable via configuration. When a proxy-header provider is enabled, the reverse proxy MUST strip any client-forged copy of the identity header and the server MUST NOT be reachable bypassing the proxy, otherwise the injected identity is forgeable and it is treated as an authorization hole. Daemons never traverse the A-layer.

**Break-glass bootstrap (orthogonal to provider selection).** A CLI-minted, console-printed, one-time admin token is the single IdP-independent escape hatch, used only for (1) first-admin bootstrap (entering to create accounts / configure a provider) and (2) a fail-closed fallback entrance when the configured provider is unreachable. It is a single admin subject, temporary / re-issuable, stored only as a hash, and never written to logs. Multiple owners are distinguished by the local provider (or an enabled OIDC), never by minting one break-glass token per user.

**Daemon credential issuance.** After login an owner generates / views / revokes their own daemon keys in the UI; the key hash is persisted and bound to that `owner_id`. A daemon presents the key in its HELLO, the server resolves `key → owner_id` and binds the reporting machine to that owner, and the UI / REST views are filtered to the owner. The daemon→server reverse trust is carried by TLS (the daemon dials a known `wss://` address whose server identity is certificate-backed); the application layer does not build a separate server-authentication mechanism, and the server itself does not terminate TLS (a reverse proxy does).

**Persistence boundary.** The server's first persistence layer is an embedded single-file sqlite store (stdlib `sqlite3`, zero external dependency). It persists ONLY the source-of-truth facts that a daemon reconnect cannot rebuild: owner records (keyed by internal `owner_id`), `(provider, external_id) → owner_id` identity-bindings, local password credential hashes, issued daemon-key hashes, and break-glass token hashes. Machine / flow / history real-time state stays in memory and is rebuilt from daemon reconnects. A future Postgres backend is a store-implementation swap behind the same repository interface.

**Security baseline.** Local passwords MUST be stored with a slow hash (argon2 preferred, bcrypt fallback) — never plaintext or a fast hash. Login MUST be rate-limited / lockout-protected against brute force. All credential comparisons MUST be constant-time. Credentials (passwords, sessions, daemon keys, break-glass tokens) MUST NOT be written to logs. The server MUST fail closed: when no usable authentication provider is configured it refuses to serve rather than reverting to the bare mode (`AuthNotConfigured` at startup), and a request that resolves to no owner is rejected with 401. UI session credentials and daemon keys are kept on separate exposure surfaces. When an OIDC provider is enabled, standard `state`/`nonce` validation and secure session attributes MUST hold.

**Channel coverage.** (a) The frontend `/ws/ui` and all `/api/*` REST routes resolve an owner via the provider chain and filter visibility / control by owner — an owner sees only its own machines / flows / history and may `POST /api/flows` / `respond` / `interject` only against its own daemons, with a cross-owner target reading as 404. (b) The daemon `/ws` resolves the HELLO key to an owner and binds the machine; a missing / invalid key is answered with `WELCOME(accepted=false)` and the socket is closed.

**Registration model.** First-boot bootstrap admin plus administrator/operator-provisioned (invited or created) users. v1 does NOT open public self-service registration (its email verification + abuse prevention + password recovery are the heaviest liabilities and there is no mail infrastructure yet); it is left as a future addition.

#### Scenario: Daemon HELLO with a valid key binds the machine to its owner
- **GIVEN** an owner has issued a daemon key (its hash bound to the owner's `owner_id` in the sqlite store)
- **WHEN** a daemon connects to `/ws` and sends HELLO carrying that key
- **THEN** the server resolves `key → owner_id`, binds the machine to that owner (`MachineRecord.owner_id`), and answers `WELCOME(accepted=true)`
- **AND** that machine and its flows are visible only to the owning owner's UI / REST views

#### Scenario: Daemon HELLO with a missing or invalid key is rejected fail-closed
- **WHEN** a daemon connects to `/ws` and sends HELLO with no key, or a key that resolves to no owner
- **THEN** the server answers `WELCOME(accepted=false)` with a key-free reason and closes the socket without entering the receive loop
- **AND** no machine record is bound to any owner for that connection

#### Scenario: REST request without a resolvable owner is rejected
- **WHEN** an `/api/*` data request arrives with no session / credential that the provider chain can resolve to an owner
- **THEN** the request is rejected with HTTP 401 (anonymous access is never admitted)

#### Scenario: Owner cannot see or control another owner's daemon
- **GIVEN** machines `M1` owned by owner `O1` and `M2` owned by owner `O2`
- **WHEN** `O1` lists machines / flows or `POST`s `/api/flows`, `respond`, or `interject` targeting `M2` (or a flow on `M2`)
- **THEN** `O1`'s machine / flow / history views contain only `O1`-owned records
- **AND** the cross-owner target reads as not-found (404) rather than being dispatched

#### Scenario: Server refuses to start when no auth provider is usable
- **GIVEN** the `server.auth` configuration leaves no enabled, usable authentication provider (e.g. local explicitly disabled and no other enabled)
- **WHEN** the server application is assembled
- **THEN** `AuthNotConfigured` is raised and the server refuses to serve — it never falls back to the identity-unaware bare mode

#### Scenario: Local passwords are slow-hashed and never logged
- **WHEN** a local credential is stored
- **THEN** the at-rest value is an argon2 (or bcrypt fallback) slow hash, never plaintext or a fast hash
- **AND** the password, session id, daemon key, and break-glass token never appear in any log line
- **AND** credential verification uses a constant-time comparison

#### Scenario: Break-glass token is one-time, hash-stored, and console-printed
- **WHEN** an operator runs `se3-server bootstrap-token`
- **THEN** a one-time admin token is minted, only its hash is persisted, and the plaintext is printed to the server console exactly once (never logged)
- **AND** consuming it via `POST /api/auth/breakglass` resolves to the single stable break-glass admin owner
- **AND** re-running the command mints a fresh token without invalidating the model's single-admin-subject invariant

#### Scenario: Non-admin is refused on every user-management endpoint
- **GIVEN** an owner whose `OwnerIdentity.is_admin` is false
- **WHEN** it calls any of `GET /api/users`, `DELETE /api/users/{owner_id}`, `POST /api/users/{owner_id}/password`, `POST /api/users/{owner_id}/admin`, or `POST /api/users`
- **THEN** each route independently rejects the request with HTTP 403, and the admin check fires before any existence check so the surface leaks nothing about which owners exist
- **AND** the rejection is enforced server-side — hiding the entry in the frontend is UX only, never the security boundary

#### Scenario: The break-glass owner is excluded from management
- **WHEN** an admin lists users via `GET /api/users`
- **THEN** the owner resolving to the reserved break-glass `(BREAKGLASS_PROVIDER, …)` binding is filtered out of the list server-side
- **AND** any `DELETE` / admin-toggle / password-reset targeting that owner is refused (reading as 404), preserving the single fail-closed escape hatch

#### Scenario: An admin cannot delete or demote itself or the last admin
- **GIVEN** the system's set of non-break-glass admins
- **WHEN** an admin attempts to delete or demote its own `owner_id`
- **THEN** the request is refused
- **AND** **WHEN** deleting or demoting some admin would empty that set (it is the last non-break-glass admin), the request is refused, with the count-check and the delete / demote write performed atomically under one held lock so a concurrent request cannot race past the invariant

#### Scenario: Password reset is restricted to local-provider users
- **WHEN** an admin calls `POST /api/users/{owner_id}/password` for an owner whose identity binding is not `local` (an OIDC or proxy-header source)
- **THEN** the reset is refused server-side (and the frontend hides the action for such users), because `local_credentials` is meaningful only for the local provider
- **AND** for a `local` owner the plaintext password is slow-hashed off the event loop and never written to any log

#### Scenario: Acting on an unknown or reserved owner_id reads as not-found
- **WHEN** a user-management mutation targets an `owner_id` that does not exist (or resolves to a reserved identity)
- **THEN** the request reads as not-found (404) rather than mutating any object

#### Scenario: Adding a second provider does not re-enroll daemons
- **GIVEN** an existing owner with a `(local, <username>)` binding and an already-issued daemon key
- **WHEN** a future provider is added and a new `(provider, external_id)` binding is linked to that same `owner_id` through the trust gate
- **THEN** the `owner_id`, the daemon→owner binding, and the issued daemon key are all unchanged
- **AND** the daemon does not need to be re-keyed or re-enrolled
