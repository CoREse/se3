# engine-internals Specification

## Purpose

Registries of the engine's auxiliary modules, per-step implementations, and merge submodules under `src/se3/engine/` — the module-boundary map sub-agents consult when CLAUDE.md is absent.

## Requirements

### Requirement: Engine Module Extensions
Besides the core modules already registered under Directory Structure, `src/se3/engine/` also contains a set of auxiliary/shared modules. New engine modules must be registered in this spec to prevent sub-agents from being unable to discover reusable module boundaries when CLAUDE.md is absent.

- **Spec processing and indexing**
  - `spec_format.py` — the Spec format v1 parser and validator; provides `parse_spec()` (splitting spec markdown into a `ParsedSpec` of a shared header plus a list of `Requirement`s) and `validate()` (v1 rule validation), and defines shared constants such as `SPEC_FORMAT_VERSION_MARKER`
  - `spec_index.py` — an item-level spec index keyed on `<spec>::<requirement>`, tracking mtime / size / sha256 prefix to support incremental invalidation; index file `se3/cache/spec-index.json` (gitignored)
  - `spec_loader.py` — the spec-loading entry point `load_for_step()`, assembling spec text for downstream steps; supports two modes: `items` (full base text + each spec's header + the selected item + 1-hop references) and `full_spec` (full base text + each spec's full text)
- **LLM output structuring**
  - `json_extractor.py` — two-phase JSON extraction: when the main call outputs non-JSON / malformed JSON, a second LLM call re-expresses the content as valid JSON, avoiding polluting the main prompt
  - `json_modes.py` — defines three LLM JSON output strategies: `STRICT` (require_json, retry on failure), `EXTRACT` (json_extract, fall back to LLM extraction on failure), and `TWO_PHASE` (two_phase_json, natural generation + LLM extraction)
  - `schema.py` — the JSON Schema / TypedDict definitions for SE3 state files (`engine.json`, `context.json`, etc.), providing structural documentation and validation capability
- **State, models, and persistence**
  - `models.py` — the core data models of the flow-engine state machine: `Step`, `State`, `Transition`, `FlowInstance`, and enums such as `StepStatus` / `FlowStatus`; fields like `State.fix_history` use a sliding window to control memory and the size of `engine.json`
  - `persistence.py` — JSON serialization/deserialization and atomic writing of flow state such as `engine.json`, preventing state-file corruption from interruptions
  - `context.py` — the `Context` class, providing read-only context for step execution and UI display, encapsulating the workflow state
  - `project_context.py` — the project-level context collector (git status, flow history, backlog, specs, etc.), consumed by the `PROJECT_SUMMARY` step and the `se3 summary` CLI
  - `baseline_fix_memory.py` — mechanism B's cross-flow persistent memory of inherited (baseline) test failures that the bounded fix loop has *given up* on, keyed per `test_id`; provides `load_given_up` / `load_given_up_details` (corruption-tolerant reads, returning an empty set/dict on a missing / corrupt / schema-mismatched store) and `record_given_up` (accumulating the attempt count and latest reason). Persists a schema-versioned JSON document atomically (tempfile + `os.replace`) to `se3/state/baseline_fix_attempts.json` (gitignored under the `/se3/*` rule), bounded to `MAX_ENTRIES` most-recently-touched ids (insertion-order LRU). Prevents every subsequent flow from re-attempting the same un-fixable baseline failure (a missing system library, a flaky test, one needing a human decision); see flow-engine *Test Step Configuration and Multi-Phase Execution*
- **Prompt / retry / history**
  - `retry_context.py` — the shared constants for retry-context formatting (`RETRY_HISTORY_MARKER` / `RETRY_HISTORY_SEPARATOR`, etc.); the producer `chat_history.format_history_for_retry` and the consumer `llm_caller._post_dedup_safety_cap` share the same API; every retry-context block must contain exactly one marker/separator pair
  - `prompt_dedup.py` — the line-level prompt deduplication tool `deduplicate_prompt_lines`, which replaces repeated consecutive line blocks (default `min_block_lines=3`) with a `[DUPLICATED CONTENT: ...]` reference to the first occurrence, reducing prompt size
  - `prompt_markers.py` — centrally defines the three-part sentinel markers separating the "system-instruction boilerplate prefix", the "user literal-input section", and the "framework follow-on injection suffix" within a step prompt (`TEMPLATE_PREFIX_END` / `USER_CONTENT_BEGIN` / `USER_CONTENT_END`, all HTML-comment literals to avoid the LLM echoing them back) and three assembly helpers (plus one read-side extraction helper, `extract_user_content`, described below): `inject_boundary(template, before)` inserts the two-part marker pair (`TEMPLATE_PREFIX_END` + `USER_CONTENT_BEGIN`) once into an existing template string, just before the `before` anchor, idempotently; `wrap_user_content(prefix, content)` directly concatenates the two strings and inserts the two-part marker; `wrap_user_section(prefix, user_content, suffix)` wraps `user_content` between `prefix` and `suffix` using all three markers, producing "prefix + TEMPLATE_PREFIX_END + USER_CONTENT_BEGIN + user_content + USER_CONTENT_END + suffix", idempotently. The read side adds a pure extraction helper `extract_user_content(content) -> Optional[str]`, the Python-side mirror of the web console's `splitUserPromptByMarker` (reusing the same three marker constants so the two implementations cannot drift): it locates the markers in canonical order and returns the middle user-content segment only when the full three-part layout is present and that segment is non-empty after its surrounding newline glue is stripped; it returns `None` (i.e. "no user literal here, fall through") when any marker is missing or out of order, when the layout is the legacy two-part `BEGIN`-without-`END` form (whose post-`BEGIN` tail is framework text, not a user literal), or when the middle segment is empty / only newlines. This shared helper is what the daemon and CLI history-title extractors call to align their titles with the chat-history user bubble (see `history.py` in *Daemon Modules* and the *`se3 history` Command* requirement of the se3-commands spec). The core constraint of the three-part semantics is: the user-content section enclosed by `USER_CONTENT_BEGIN` / `USER_CONTENT_END` may contain only "literal input coming from the user" (such as discovery's `initial_description` / `user_response`, interjection.text, etc.); any other string that the se3 framework itself writes (Project Context / Available Specs / Discovery Context wrapper layer / JSON format constraints / Guidelines / language instructions / Runtime Environment injection / READ-ONLY CONSTRAINT, etc.) belongs to the prefix or the suffix. Every step prompt module (analyze / plan / plan_tasks / implement's `IMPLEMENT_PROMPT` / `IMPLEMENT_GROUP_PROMPT` / `FIX_PROMPT` / discovery initial and follow-up / self_check / verify_spec / update_spec / summarize / version_analyze) must call one of these at the template-assembly point: a step with genuine user literal input (currently in practice only discovery) uses `wrap_user_section`, while a step with no user literal input may keep using the two-part marker of `inject_boundary` / `wrap_user_content`. `wrap_user_content` / `inject_boundary` are retained as compatibility entry points; the two-part marker they produce degrades, in frontend recognition, to "prefix + empty user-content + whole suffix". This protocol lets the web running-flow console split a user message into "a system-prefix chip collapsed by default + a user-content bubble expanded by default + a collapsed framework suffix" (see the *Role-Based Message Collapse* requirement of the running-flow-console spec); an old user message with incomplete or missing markers falls back to a single whole chip
  - `prompt_history.py` — interactive prompt history based on `prompt_toolkit` `FileHistory` (default directory `history/`, filename `prompt_history`, `MAX_ENTRIES=500`), supporting up/down arrow browsing of past input
  - `sync_history.py` — a lightweight flow context for the sync flow (`SyncFlowContext`), generating `flow_id` / `step_id` so that `LLMCaller` can automatically record sync's prompt/response through the existing ChatHistory infrastructure
- **Human-interaction call files**
  - `interaction_calls.py` — the unified call-file channel (`se3/calls/`) for every point in a running flow that needs human intervention. Each pending interaction — a pending-response MCP call, a Ctrl-C mid-flight interjection, a retry/failure decision, a CLI subprocess confirmation prompt, the non-interactive discovery confirmation gate (`discovery_confirm`, carrying one-click confirmation `options` whose `value` is `"1"`) — converges into the same kind of `kind`-tagged JSON file (with `kind` drawn from the `CALL_KIND_*` constants in `protocol.py`), carrying display metadata such as `prompt` / `context` / `options` so the daemon aggregator and the web console can render and route without guessing at the text. Provides `write_call` / `read_call` (an old call file lacking the `kind` field defaults to `CALL_KIND_CALL`, preserving backward compatibility) / `read_response` / `write_response`, `write_retry_decision_call` (the no-TTY failure-decision call), `write_interjection_request` (daemon-side interjection writing) / `drain_interjection_requests` (consumed at `se3 run` step boundaries), and `make_cli_confirm_handler` (bridging a CLI subprocess confirmation prompt into a `cli_confirm`-kind call and writing the answer back to the subprocess stdin)
- **Tasks and dependency graph**
  - `task_description.py` — the Task-description composition tool that renders the extra instructions the user entered during a Ctrl-C interruption (persisted in `flow.state.context["user_interjections"]`) into a unified `## Additional Instructions (added during run)` section, guaranteeing that `run.py:_handle_step_interrupt` and `state_machine._build_step_inputs` produce byte-identical output
  - `transitive_reduction.py` — the transitive reduction `transitive_reduce(groups)` of the task-group dependency DAG, removing redundant `depends_on` edges derivable through other paths
  - `stash_utils.py` — shared helper functions for `git stash pop` conflict recovery, shared by the DAG implement step (merging a leaf branch back into the parent worktree) and the `se3 merge` robust strategy (stashing a dirty working tree)
- **Truncation and formatting**
  - `truncation.py` — the shared truncation constants for LLM-consumed content, centrally maintaining the stdout/stderr tail-truncation limits for steps such as `self_check` / `verify_spec` / `test`, ensuring consistency and meeting the lower-bound requirement of the flow-engine spec's "LLM Content Truncation Strategy"
  - `output.py` — the flow engine's core output formatting tool; user-visible content is delegated to `display.py` to render in full (no longer truncated)
  - `output_formatter.py` — the output-formatter registry, centrally registering and looking up formatters by name
  - `display.py` — the full-content rendering tool (based on `rich`), used to display LLM output, spec, proposal, design doc, etc. without truncation
  - `tool_formatters.py` — per-tool `tool_use` / `tool_result` preview formatters based on the `TOOL_FORMATTERS` dict registry, shared by `llm_caller.py` (streaming output) and `chat_history.py` (history review); unknown tools fall back to a generic formatter
  - `step_renderers.py` — the step-output rendering registry, providing the single entry point `render_step_output`, dispatching renderers by step type, with unregistered types using a default generic renderer
  - `logging_config.py` — structured (JSON-format) logging configuration, providing step tracing, latency, and LLM metrics
- **Event stream and pluggable sinks**
  - `event_stream.py` — the unified structured event stream of `se3 run`: defines the `EventType` enum (`flow_started` / `step_started` / `step_output` / `step_completed` / `step_failed` / `flow_paused` / `flow_completed` / `flow_failed` / `interjection_needed` / `call_needed`), the `Event` dataclass, the `new_event` factory function, and the in-process pub/sub emitter `EventEmitter` (`subscribe` / `unsubscribe` / `emit` / `scope`). `se3 run` internally emits only this one stream and is unaware of the caller
  - `sink.py` — pluggable sinks at the end of the event stream: the `Sink` ABC (`consume(event)`) and three concrete implementations — `CliSink` (delegates rendering to the existing `step_renderers.py`, keeping CLI output byte-for-byte compatible; and via `_CLI_SKIP_STEP_TYPES`={`confirm`,`discovery`,`plan`} skips terminal-event rendering for these interactive/special steps, because their CLI output is presented by the orchestrator's interactive/dedicated paths and re-rendering would duplicate output), `JsonSink` (serializes events as NDJSON for consumption in daemon mode), and `HistorySink` (appends `step_completed` events to the per-step jsonl history file, for the daemon `history.py` to report incrementally, from which the web console renders a structured report card expanded by default for each step; the CLI history viewer `chat_history.get_step_history` actively skips such records to avoid duplicate rendering). `HistorySink` is unconditionally subscribed by `src/se3/commands/run.py` in `_run_flow_impl`, unaffected by `--output-format`. The orchestrator now emits a terminal event for **every** step type (including the interactive `confirm`/`discovery`, `plan`, `summarize`) on a terminal result (`COMPLETED`/`PARTIAL`/`FAILED`), so that `HistorySink`/`JsonSink` can persist and forward its structured output; the above `CliSink` skip ensures CLI output is not re-rendered. "CLI vs daemon" degrades to a single `CliSink`/`JsonSink` choice under the outermost `--output-format` switch
- **Subpackages**
  - `formatters/` — the output-formatter subpackage; currently contains concrete formatter implementations such as `task_formatter.py`, registered by `output_formatter.py`
  - `utils/` — the engine-internal generic-utility subpackage; currently contains shared parsing helpers such as `json_parser.py`

### Requirement: Engine Step Implementations
`src/se3/engine/steps/` is the implementation package for each step of the `se3 run` state machine, dispatched by step type by `engine/state_machine.py` as the flow advances. Each step module encapsulates a single flow phase; new steps must be registered in this spec to prevent the LLM subprocess from being unable to discover the available step boundaries and responsibility division when CLAUDE.md is absent.

- `analyze.py` — the analyze step; performs requirements analysis and impact assessment of the user's task, identifies the relevant specs / code modules, and produces the input context for the subsequent plan / implement
- `plan.py` — the plan step; building on analyze, outputs the implementation plan (step breakdown, risk points, verification strategy) as the instruction source for implement
- `plan_tasks.py` — the task-level plan step; further breaks down the overall plan into task groups executable by the DAG scheduler (including `depends_on` dependencies), for `engine/dag_scheduler.py` to schedule
- `implement.py` — the implement step; performs the actual code changes per the plan / plan_tasks output, working with `engine/worktree.py` to complete the implementation inside an isolated worktree
- `verify_spec.py` — the verify_spec step; verifies whether the implementation artifacts satisfy the relevant spec requirements; the truncation strategy for its LLM-consumed content follows the centrally maintained limits in `engine/truncation.py`
- `test.py` — the test step; runs the project test suite and parses the results; stdout/stderr truncation follows the shared limits in `engine/truncation.py`
- `test_with_fail_loop.py` — a test-step variant with a failure loop; on test failure it drives a fix sub-flow and re-runs, constrained by the `max_fix_iterations` fix-loop cap enforced by `engine/state_machine.py`
- `self_check.py` — the self_check step; the agent performs a self-check of the current phase's artifacts; truncation limits are likewise centralized in `engine/truncation.py`
- `_fix_context.py` — a private helper module that builds context (such as failure summaries, historical diffs, etc.) for fix / retry steps; not exposed directly as a step
- `commit.py` — the commit step; invokes logic equivalent to `se3 commit` to land changes; enforces passing tests, intercepts sensitive files, and ensures the commit message contains context
- `confirm.py` — the confirm step; requests confirmation from the user/agent at key junctures (such as approach selection, risk acceptance), collaborating with interaction modules like `engine/sync_interaction.py`
- `discovery.py` — the discovery step; works with `engine/issue_discovery.py` to scan code / spec and produce issue drafts
- `project_summary.py` — the project_summary step; calls `engine/project_context.py` to collect project-level context and produce a summary (also providing the data source for the `se3 summary` CLI)
- `summarize.py` — the summarize step; generates markdown / JSON summary snapshots of the current flow's phase outputs, writing them to `se3/state/summary-*.md` / `summary-*.json`
- `update_spec.py` — the update_spec step; performs controlled updates to the relevant spec files based on implementation / test results; write paths are restricted to `se3/specs/**/spec.md` and are subject to the spec guardrails check
- `spec_gate.py` — the spec_gate step (mechanism A): the post-`update_spec` verification gate inserted between `update_spec` and `version_analyze` in the `feature` / `discovery` sequences; a pure program step (no LLM) that, only when the flow actually changed a spec, first runs the programmatic artifact check (`spec_validator.validate_spec_structure` + a requirement count/name non-decrease check on edited specs relative to the stable pre-`update_spec` snapshot) and then re-runs the full test suite through the shared `steps/test.py::run_and_classify_tests` core; routes back to `update_spec` on an invalid artifact or to `implement` on an introduced test failure; also exports `build_spec_requirement_baseline`, the canonical builder of the pre-`update_spec` spec snapshot shared with the state machine (see flow-engine *Post-update_spec Spec Verification Gate*)
- `version_analyze.py` — the version_analyze step; based on the current flow's commit type (bugfix / feature) and the version baseline from `engine/version_bumper.py`, analyzes and prepares the input needed for the version bump
- `conftest.py` — a pytest configuration file scoped to the `src/se3/engine/steps/` subpackage, used to prevent step implementation modules (especially the one named `test.py` and step files prefixed with `test_`, such as `test_with_fail_loop.py`) from being mistakenly collected by pytest as test cases; this file is not a step implementation but the pytest collection-behavior configuration for this directory, existing as a controlled exception to the Engine Step Implementations constraint that "each step module encapsulates a single flow phase"

### Requirement: Engine Merge Submodules
The `src/se3/engine/merge/` package is the implementation core of the `se3 merge` flow, responsible for orchestrating multi-branch merging, LLM conflict resolution, spec guardrails, runtime data synchronization, and version aggregation into one end-to-end flow. Each submodule has a clear responsibility; new merge submodules must be registered in this spec to prevent the LLM subprocess from being unable to discover the merge flow's module boundaries when CLAUDE.md is absent.

- `orchestrator.py` — `MergeOrchestrator`, the overall orchestration that merges multiple branches sequentially into the current branch: calls `git merge` for each branch, dispatches the clean merge / conflict / non-conflict failure paths, invokes guardrails, and aggregates the per-branch results
- `conflict_context.py` — `ConflictContextBuilder`, collects the three-way merge context for LLM conflict resolution: ours/theirs branch names, the merge-base SHA, HEAD commit info, the four versions of each conflicted file (base/ours/theirs/working tree, including `<<<<<<<` markers), hunk line ranges, the oneline log between base and each side, and spec-file identification; includes magic-byte-signature-based binary-file detection
- `conflict_resolver.py` — `ConflictResolver`, builds a prompt from `ConflictContext` and calls `LLMCaller`, parsing the structured JSON response (resolved content, per-hunk confidence, flags); by default caps resolved file content at 5 MiB to guard against OOM
- `strategy.py` — `StrategyDecider`, the safe/strict/fast three-strategy decision matrix; selects a `DecisionAction` based on the LLM resolution's confidence, the spec guardrail flags, and the file type
- `guardrails.py` — `MergeGuardrailsCheck`, runs guardrails after a merge against the changed spec files under `se3/specs/**/spec.md`, detecting deleted requirements, weakened language, and weakened quantifiers; also exports the reusable pure function `check_spec_diff()` shared with the `se3 guardrails` CLI
- `guardrail_repair.py` — `GuardrailRepairer`, LLM-driven spec repair when guardrails flag a violation under the fast strategy: builds a repair prompt, calls the LLM, parses the corrected content, writes it back to the working tree, commits the repair (preferring a fix-up commit on top of the merge commit, falling back to amend), and re-runs guardrails to verify the repair; all write-back paths are restricted to `se3/specs/**/spec.md`, and `pre_amend_sha` must be saved before amending to support precise rollback
- `human_call.py` — `HumanCallWriter`, when LLM conflict resolution triggers a HUMAN_CALL decision, writes a structured call file to `se3/calls/` containing the conflict context, the LLM resolution, and the decision options for human review (the response file is handled by `se3 merge-respond`)
- `cleanup.py` — `CleanupManager`, implements the `--delete-merged` flag: safely deletes fully merged branches and their bound worktrees with `git branch -d` (lowercase); skips protected branches (main / master / the current branch); refuses to clean up a dirty worktree; runs git subcommands with `LC_ALL=C` to match English stderr; explicitly validates with `git merge-base --is-ancestor` before deletion. Its `_archive_worktree` helper lands each deleted worktree's backup at `project_root/se3/worktrees/.archive/<slug>-<ts>/` — inside the sole `/se3/*`-ignored runtime root `se3/` (previously `project_root/.se3/archive/`, which was covered by no gitignore rule and thus leaked the backup into git); the slug-timestamp naming with conflict-sequence suffix, the `shutil.copytree` behavior, and the `.se3-archive-meta.json` metadata write are otherwise unchanged
- `runtime_sync.py` — runtime data synchronization after a successful merge: the git-ignored runtime data under `se3/` is not automatically merged by git merge, so this module copies the tier A runtime content from the source branch's bound worktree into the current branch's `se3/` directory, and fixes the TOCTOU window of the leaf-symlink swap
- `version_aggregator.py` — after all branches have been merged sequentially, infers the SemVer bump type relative to the merge-base of each branch and the pre-merge HEAD, applies the largest bump to `pyproject.toml`, and amends the last merge commit; includes atomic write-temp + `os.replace` writing, fail-loud on `Version.parse` failure, explicit distinction of `version_already_at_target` (the `VersionNotAdvanced` exception class), a lenient TOML version regex (matching both `version="1.2.3"` and `version = "1.2.3"`), and synchronized restoration of both the pyproject.toml content and the staging area on the failure path
